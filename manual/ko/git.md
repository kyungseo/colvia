# Git과 함께 쓰기

[사용 설명서](README.md) · 한국어 · [English](../en/git.md)

Git 저장소에서도 먼저 [폴더 연결을 요청](install.md#connect)하세요. Git이 아직 등록되지 않았다면 연결 미리보기가 멈추고 먼저 등록하도록 안내합니다. 아래 절차로 등록을 검토·승인한 뒤 연결 미리보기를 요청하세요. 같은 계정에 이미 등록한 Git은 다른 프로젝트에서도 사용할 수 있습니다. 결과를 수락하는 일과 그 결과를 Git에 반영하는 일은 별개의 결정입니다.

[Git 등록하기](#git-register) · [명령으로 등록하기](#git-register-cli) · [Git에 결과 반영하기](#git-integration) · [중단된 Git 반영 복구하기](#git-recovery)

아직 Git을 쓰지 않는 폴더를 처음 연결한다면 “이 폴더를 연결하면서 Git도 시작해 주세요”라고 요청할 수 있습니다. [가능한 조건과 연결 미리보기](install.md#first-git)를 확인하세요.

<a id="git-and-colvia-records"></a>

## Git에 파일 이력이 남는데, Colvia 기록이 따로 필요한가요?

범위를 승인하거나 수정 요청을 남길 때는 아직 Git에 커밋할 내용이 없을 수도 있습니다. 수락한 파일은 Colvia에 남습니다. 예를 들어 보고서를 수락한 뒤 같은 작업 폴더에서 다른 브랜치로 바꾸면, 그때 수락한 본문을 다시 열고 지금 브랜치의 보고서와 비교할 수 있습니다.

수락한 파일을 나중에 커밋하면 그 내용은 Git에도 남습니다. 동료가 브랜치를 받아도 내 승인 내역이나 수정 요청까지 받지는 않습니다. [기록을 저장하는 위치와 이유](architecture.md#why-local-records) · [중단된 Git 반영 복구하기](#git-recovery)

팀이 저장소에 함께 둔 설계 문서에는 그 결정을 내린 이유를 적어 동료와 공유할 수 있습니다. 한편 검토자가 제안서 어느 판을 보고 어떤 수정을 요청했는지는 그 작업을 기록한 기기의 Colvia에서 다시 찾을 수 있습니다. 동료가 저장소를 복제하면 커밋한 문서를 받습니다. 기기에 있는 Colvia 기록은 따로 보관됩니다.

<a id="adopt-git"></a>

## 쓰던 폴더를 Git으로 관리하기

같은 폴더에서 “이제 이 폴더를 Git으로 관리하고 싶어요”라고 요청하세요. 계정에 사용할 Git을 [등록](#git-register)한 뒤, 에이전트가 전환할 폴더와 기존 작업 수를 확인합니다. Git이 없으면 빈 `main` 브랜치를 만들고, 이미 `git init`을 했다면 현재 저장소를 그대로 사용합니다. 미리보기를 보고 승인하세요. 작업 파일, 스테이징한 부분, 기존 Work와 수락한 제출본이 그대로 남습니다. 첫 커밋과 원격 저장소 연결은 원할 때 따로 요청하세요.

전환은 Colvia 기록과 같은 볼륨에 있는 단일 프로젝트 루트에서 가능합니다. 진행·검토·일시정지 중인 Work를 비롯해 미완료 Work가 있으면 전환을 기다립니다. Git을 아직 초기화하지 않았다면 기존 Work를 먼저 마칠 수 있습니다. 하위 모듈, 연결된 worktree, 진행 중인 Git 작업 또는 Git이 추적하는 기존 Colvia 연결 표식도 먼저 확인해야 합니다.

하던 Work가 있는 폴더에서 직접 `git init`을 했다면 원래 폴더에서 “Git으로 전환하기 전에 작업 기록을 백업하고 하던 일을 마치고 싶어요”라고 요청하세요. Colvia가 원래 연결과 저장소를 확인합니다. 기존 계획이나 제출본을 보고, 일시정지한 Work를 재개하거나 승인한 범위 안에서 수정해 제출할 수 있습니다. Git이 무시하는 파일도 범위 밖 변경 검사에 포함됩니다. 그만둘 Work는 폐기 미리보기를 보고 따로 결정하세요. 폐기한 뒤에도 기존 승인과 제출본을 볼 수 있습니다.

직접 조회하려면 macOS에서 `./colvia --finish-plain-work ordinary list`, Windows PowerShell에서 `.\colvia.cmd --finish-plain-work ordinary list`를 실행하세요. [기록 백업 안내](records.md)를 따를 때도 `backup export` 앞에 같은 옵션을 붙이고, 백업 파일과 임시 작업 폴더는 프로젝트 밖에 두세요. 처음 승인을 기다리는 Work는 이 모드에서 계획을 확인하거나 명시적으로 폐기할 수 있습니다. 모든 Work를 마치거나 폐기하면 Git 전환을 미리보고 승인하세요. 스테이징한 내용도 유지됩니다.

전환 중 멈추면 에이전트에게 “아까 하던 Git 전환을 이어가 줘”라고 요청하세요. 같은 작업 ID로 이어가며, 그사이에 작업 파일이나 스테이징이 바뀌었으면 현재 상태를 확인하고 다시 승인합니다. 재확인 화면에서는 변경된 Git 항목과 작업 파일·스테이징 경로의 예를 볼 수 있습니다. 다른 Git 프로그램이 인덱스를 갱신한 경우에도 확인을 요청할 수 있습니다. Colvia가 폴더를 변경하기 전에 다른 프로그램이 먼저 Git을 초기화했다면 전환 예약을 취소하고 기존 저장소로 다시 미리보세요. 전환 전에 수락한 결과는 계속 조회할 수 있습니다. 그 내용을 새로 수정하거나 Git에 반영하려면 새 Work에서 범위를 정하세요.

## Git 등록하기

Git 등록은 운영체제 계정의 Colvia 설치에 적용되며, 프로젝트마다 반복할 필요는 없습니다. 이미 등록한 Git을 그대로 사용할 경우 [저장소의 최상위 폴더 연결](install.md#connect)을 요청하세요. Git 없이 계속 쓰는 폴더에는 등록이 필요 없습니다.

연결 미리보기에서 Git 등록을 안내받았거나 미리 등록해 두려면 다음처럼 요청하세요.

> 이 프로젝트에서 쓰는 Git을 Colvia에 등록해 주세요.

에이전트가 현재 환경에서 쓰는 Git 실행 파일을 찾아 등록 미리보기를 준비할 수 있습니다. 경로가 여러 개라면 실제로 쓰는 Git을 골라 주세요. 미리보기에서 경로를 확인하고 등록을 승인하면, 에이전트가 미리보기 원본으로 등록을 적용합니다. 기존 등록을 바꾸는 경우에는 교체할 경로를 확인하고 별도로 승인하세요. 교체한 등록은 이 계정에서 등록된 Git을 사용하는 모든 프로젝트에 적용됩니다. 등록을 확인한 뒤 저장소의 최상위 폴더에서 [연결을 요청](install.md#connect)하세요.

앱이나 CLI가 등록에 필요한 경로나 실행을 막으면, 에이전트에게 어느 접근이 필요한지 확인하세요. 앱에서 필요한 범위만 허용할 수 있으면 그 방법을 쓰고, 직접 진행하려면 [아래 명령](#git-register-cli)을 사용하세요.

<a id="git-register-cli" name="git-register-cli"></a>

### 명령으로 Git 등록하기

신뢰하는 Git 설치의 실행 파일을 지정하세요. Windows PowerShell에서 `(Get-Command git).Source`로 사용 중인 Git 경로를 확인할 수 있습니다. 일반 PowerShell은 설치에 사용하고, 미리보기 원본을 파일로 저장할 때는 명령 프롬프트(cmd.exe)를 사용하세요. Windows PowerShell 5.1의 `>` 또는 `Out-File`은 출력의 인코딩을 바꿀 수 있습니다.

**Windows.** 명령 프롬프트에서 아직 `git-registration.json`이 없는 로컬 NTFS 폴더를 사용하세요. 아래 예의 Git 경로는 방금 확인한 실제 절대 경로로 바꾸세요.

```cmd
"%LOCALAPPDATA%\Colvia\bin\colvia.exe" manage git-register-preview "C:\Path\To\Git\cmd\git.exe" > git-registration.json
```

이 미리보기는 Git을 실행하지 않습니다. 저장한 파일을 읽어 Git 경로, 파일 해시, `receipt` 값을 확인하세요. `receipt`는 미리보기에 들어 있는 확인값입니다. 파일을 편집하거나 다시 저장하지 마세요. 미리보기에서 오류가 나면 그 파일을 적용하지 마세요. 안내된 원인을 해결한 뒤 다른 이름으로 새 미리보기를 저장하세요. 검토 후 등록을 승인했다면 같은 명령 프롬프트에서 아래의 `RECEIPT_FROM_PREVIEW`를 그 값으로 바꿔 적용하세요. 기존 등록을 바꿀 때는 교체를 확인한 뒤에만 `--replace`를 붙입니다.

```cmd
"%LOCALAPPDATA%\Colvia\bin\colvia.exe" manage git-register --plan git-registration.json --receipt "RECEIPT_FROM_PREVIEW"
```

**macOS.** 아직 `git-registration.json`이 없는 로컬 폴더에서 터미널을 여세요. 아래의 `/path/to/git`은 사용 중인 Git 실행 파일의 절대 경로로 바꿉니다. 미리보기를 저장해 위와 같은 방식으로 검토한 뒤, 등록을 승인했다면 `RECEIPT_FROM_PREVIEW`를 확인값으로 바꿔 적용하세요.

```sh
"$HOME/Library/Application Support/Colvia/bin/colvia" manage git-register-preview "/path/to/git" > git-registration.json
"$HOME/Library/Application Support/Colvia/bin/colvia" manage git-register --plan git-registration.json --receipt "RECEIPT_FROM_PREVIEW"
```

미리보기를 검토하고 등록을 승인하면 Colvia 관리자가 선택한 실행 파일의 해시를 다시 확인한 뒤 Git 버전을 조회합니다. 해시는 그 실행 파일만 다루므로 Git 설치 출처와 함께 설치된 구성요소도 신뢰할 수 있어야 합니다.

<a id="git-worktree-registration" name="git-worktree-registration"></a>

## 등록된 worktree 때문에 명령이 멈췄을 때

Git에 등록된 worktree(별도 작업 폴더)가 사라졌거나 등록에 `bare` 항목이 있으면, Colvia는 연결 미리보기나 이미 연결한 프로젝트의 명령에서 저장소 구조를 확인하다 멈출 수 있습니다. 에이전트에게 문제가 된 등록을 보여 달라고 요청하세요. 직접 살펴보려면 Git 저장소에서 아래 명령을 실행하세요.

```sh
git worktree list --porcelain
```

- `prunable` 표시가 있으면 경로부터 확인하세요. 폴더를 옮겼거나 드라이브에 접근할 수 없다면 원래 경로에서 접근을 복구하세요. 실제로 사라진 폴더라면 저장소 관리자에게 해당 경로의 브랜치·작업 파일·스테이징을 확인하고 필요한 자료를 보존한 뒤 그 등록을 정리해 달라고 요청하세요.
- `bare` 표시가 있으면 작업 폴더 없이 Git 데이터만 가진 저장소입니다. 지원 조건을 충족하는 일반 Git 작업 폴더가 있는지 저장소 관리자에게 확인해 달라고 요청하세요.

Git의 일괄 정리 명령은 여러 등록에 영향을 줄 수 있습니다. `.git` 내부와 다른 worktree 등록을 보존하고, 관리자가 확인한 조치 뒤 막혔던 명령을 다시 확인하세요. 연결 중에 멈췄다면 [연결 미리보기](install.md#connect)를 다시 확인하세요.

## Git에 결과 반영하기

[수락한 결과](#git-and-colvia-records)를 Git에 반영하려면 반영할 파일과 변경 미리보기, 현재 스테이징 상태를 확인하고 별도로 승인하세요.

<a id="git-credential-check" name="git-credential-check"></a>

### 자격증명 검사에서 멈췄을 때 · v0.2.0

Colvia는 Git 객체를 만들기 전에 선택한 파일의 내용과 경로, 커밋 메시지, 브랜치 이름, 작성자 이름·이메일, 실행 ID를 내 기기에서 검사합니다. 알려진 형태의 키·토큰, 개인 키, URL 안의 비밀번호, 설정에 직접 적은 비밀값을 찾습니다. 한 번에 처음 발견한 위치만 알려 주고 값은 숨깁니다. 수정본을 제출하기 전에 에이전트에게 “반영할 다른 파일에도 같은 종류의 값이 있는지 확인하고 위치만 알려 주세요”라고 요청할 수 있습니다. 내용을 검사해 알아낸 유형과 행 번호가 있으면 함께 표시합니다. 예를 들어 Python 코드에 직접 적은 API 키는 `api_key = os.getenv("OPENAI_API_KEY")`처럼 환경변수를 읽도록 고친 뒤 수정본을 다시 제출하고 수락하세요. 메시지에서 발견했다면 메시지만 고치세요. 이 검사는 Colvia를 통해 Git에 반영할 때 적용되며, 이미 저장한 Work와 Git 이력은 원래 내용을 유지합니다.

`.env`, `.env.local`, `.env.production`과 `secrets/` 폴더 아래의 파일은 내용과 관계없이 추가·수정이 차단됩니다. 프로젝트 안 어느 폴더에서든 같은 규칙을 적용하며 대소문자를 구분하지 않습니다. 공유할 설정은 `secrets/` 밖에 `.env.example`이나 `.env.template`으로 두고 실제 값 대신 환경변수를 참조하세요. 예시 파일도 내용 검사를 거칩니다. `.netrc`(Windows의 `_netrc` 포함), Terraform 상태 파일 `*.tfstate`와 백업 `*.tfstate.backup`, `*.tfstate.<숫자>.backup`도 추가·수정이 차단됩니다. 키 저장소(`.p12`·`.pfx`·`.jks`·`.keystore`)도 보호 경로로 취급합니다. 이미 추적 중인 보호 파일을 삭제할 때는 미리보기에 삭제 사실만 표시합니다.

`.npmrc`는 프로젝트에서 공유할 수 있습니다. `_authToken`, `_auth`, `_password` 같은 인증 항목에 값을 직접 적으면 Git 반영이 멈춥니다. 레지스트리 주소와 설정은 두고 인증값을 `${NPM_TOKEN}`처럼 환경변수로 참조하세요. 기존 토큰을 환경변수 참조로 바꾸면 미리보기에 새 설정만 표시됩니다.

같은 커밋에서 보호 파일을 지우면서 원래 내용을 다른 파일에 그대로 넣으면 이름을 바꿔도 반영이 멈춥니다. 자격증명이 들어 있던 `.npmrc`를 지우거나 고칠 때도 다른 반영 대상에 원본과 똑같은 내용이 남아 있으면 멈춥니다. 공유할 파일에서 실제 값을 제거한 뒤 수정본을 제출하세요.

**이미지·글꼴을 함께 반영할 때** PNG, JPEG(`.jpg`·`.jpeg`), GIF, WebP, ICO 이미지와 WOFF, WOFF2, TTF, OTF 글꼴은 확장자와 파일 앞부분의 서명이 일치해야 합니다. Colvia는 해당 파일의 본문을 자격증명 검사에서 건너뜁니다. 미리보기의 `내용 검사 안 함: "logo.png" (PNG)`과 JSON 결과의 `unchecked_assets`에서 파일별 경로와 형식을 확인한 뒤 반영을 승인하세요. 보호 경로와 원본의 동일 사본에 대한 차단은 이 파일에도 적용됩니다. SVG는 텍스트로 검사합니다.

**그 밖의 파일에서 멈췄을 때** 서명이 맞지 않는 이미지·글꼴, PDF, 압축 파일, 데이터베이스 및 실행 파일 등 지원하지 않는 이진 파일은 Git 후보 준비가 중단됩니다. 해당 파일을 포함하지 않는 Work를 골라 먼저 반영할 수 있습니다. 별도 커밋이 꼭 필요하면 파일을 직접 검토하고 Git으로 커밋하세요. 개인 키와 실제 비밀번호는 커밋 대상에서 빼세요. 텍스트는 UTF-8이어야 하며, 단 한 줄이라도 256 KiB를 넘으면 중단됩니다. 한 줄로 압축된 JS나 CSS도 같은 한도가 적용됩니다.

같은 파일의 기존 내용에 자격증명이 있거나 기존 내용을 검사할 수 없으면 삭제 사실 또는 새 내용을 보여주고 이전 본문은 숨깁니다. 이전 Git 미리보기에 그대로 표시할 수 없는 내용이 있다는 안내가 나오면 새 미리보기를 준비하세요. 후보를 준비하면 Git 객체가 만들어집니다. 현재 브랜치와 스테이징 영역에 반영하는 일은 후보를 검토한 뒤 별도로 승인합니다.

### 스테이징과 저장소 상태 확인

Colvia는 다른 파일에 스테이징한 변경을 보존합니다. 선택한 파일의 스테이징 내용이 현재 커밋과 수락한 결과 중 어느 쪽에도 맞지 않으면, 스테이징한 변경을 보호하기 위해 Git 반영을 멈춥니다.

작업 중 branch를 바꾸거나 pull·rebase로 기준이 바뀌면 자동으로 새 기준을 승인하지 않습니다. 범위 밖 변경을 숨기지 않고, 이어갈 방법을 확인합니다. 프로젝트 하위 폴더의 독립 연결이나 Git 사용 여부가 바뀐 폴더의 자동 전환은 현재 Preview의 지원 범위 밖입니다. 심볼릭 링크와 submodule은 그대로 보호할 수 있지만 편집 대상으로 삼지 않습니다.

Git hook이 있거나 자동 통합 조건을 만족하지 않으면 Colvia가 임의로 hook을 끄거나 index를 초기화하지 않습니다. 수동 Git 작업으로 이어갈 때도 수락한 결과와 commit할 내용을 다시 대조하세요.

<a id="git-recovery" name="git-recovery"></a>

## 중단된 Git 반영 복구하기

Colvia의 Git 반영이 중단됐다면 `index.lock`을 지우거나 새 commit을 만들지 마세요. 원본 index를 보존하는 도중 현재 index가 잠시 없을 수 있습니다. 통합 상태를 조회하고 복구 경로로 이어가며, 잠금 소유자를 확인하지 못하면 먼저 진단해야 합니다. Windows의 Git 반영은 같은 볼륨의 준비 공간이 필요하며, 실행 비트가 없는 hook 파일도 활성 hook으로 취급합니다.

Windows에서 Colvia의 Git 반영이 중단되면 에이전트에게 “중단된 Git 반영 상태와 잠금 위치를 확인해 줘”라고 요청하세요. Colvia가 잠금 파일을 옮기기 전에 남긴 기록과 현재 파일이 일치하면 상태 확인 뒤 복구를 이어갈 수 있습니다. Git 반영 전 중단이면 이번 반영을 하지 않은 상태로 정리하고, 이미 반영을 시작했다면 승인된 변경의 완료 여부를 확인합니다. 다른 Git 프로그램의 잠금, 변경된 파일, Colvia가 만든 것으로 확인할 근거가 없는 잠금은 자동으로 가져오거나 지우지 않습니다. 다른 Git 작업이 끝났는데도 계속 막히면 중단 기록을 보존해 진단을 요청하세요. Work 수락과 새 Git 반영 승인은 이 복구와 별개입니다.
