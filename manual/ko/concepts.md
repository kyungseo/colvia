# 첫 작업에 필요한 기록과 결정

[사용 설명서](README.md)

현재 사용법은 [Work에 남는 기록](understand.md)과 [일을 맡기는 예시](work-guide.md)에서 확인하세요. 아래의 상세 기록 예시는 이전 entry-1 구성을 기준으로 합니다.

첫 프로젝트에서는 프로젝트 계획, 수락할 작업 요청서, 그 요청서를 수행하는 Work를 구별하면 됩니다. 사람은 Markdown 설명을 읽고, Colvia는 정확히 어느 판본이 수락됐는지 식별하는 기록을 보관합니다.

## 계획·작업 요청서·Work

| 용어 | 뜻 | 할 일 프로젝트 예 |
| --- | --- | --- |
| 프로젝트 계획 | 목표, 순서, 앞으로 할 일을 설명하는 프로젝트 소유 문서 | 추가·조회부터 만들고 삭제는 나중에 검토 |
| 작업 요청서 초안(intent draft) | 목표·범위·기대 결과·검사·목적지·제외 범위를 담은 제안 | 수락 전의 추가·조회 기능 제안 |
| 수락된 작업 요청서(accepted intent) | 사람이 수락해 선택된 정확한 요청서 판본 | 정해진 네 파일 범위의 작업 권한 |
| 작업(Work) | 수락된 요청서를 수행하는 단위. 계획·진행·검토·결과 기록을 포함 | 시작 기준, 구현, 제출한 결과, 수락 결정 |
| 후보(candidate) | 기록된 가능성이나 계획상의 선택 | “다음에 잘못된 데이터 처리를 검토하자” |

후보 선택은 작업 요청서 수락이 아닙니다. 작업 요청서를 수락했다고 미래의 결과까지 수락한 것도 아닙니다. Work의 완료 상태는 수락된 결과가 선택돼 있을 때 도출됩니다.

## 누가 무엇을 맡는가

프로젝트의 상태·수락·이력을 판단하는 기준 기록은 한곳에 모입니다. 이 저장 위치를 *authority home*이라 부르며 현재 경로는 `.hrn/`입니다. 프로젝트 Markdown은 목적·계획·결과를 설명하며 정해진 형식의 수락 기록을 대신하지 않습니다.

```text
사람(Owner) ── 범위와 수락을 결정
       │
       v
Agent ── 제안 준비, 승인된 구현, 결과 설명
       │ 검증된 명령 사용
       v
.hrn/ ── 프로젝트 소유의 작업 요청서·Work·이력 기록
       │ 읽기 전용 조회
       v
View ── 사람과 agent가 읽는 현재 관측 결과

프로젝트 README / 계획 / Work 문서 ── 사람이 읽는 설명
```

그림은 책임을 구분한 것이며 자동 orchestration을 뜻하지 않습니다. 기록의 actor 이름은 신뢰하는 로컬 계정 안에서 역할을 나타내고, 인증된 신원은 아닙니다. [기본 개념 계약](../../docs/CONCEPTS.md)을 참고하세요.

`View`는 검증된 기록과 현재 관측을 보여주는 읽기 전용 결과입니다. 상태를 바꾸거나 수락을 결정하지 않습니다. 출력은 주로 영어이며 일부 현지화된 내용이 포함된 진단용 Markdown입니다. agent가 사용자의 언어로 설명해야 합니다. 판단을 내리기 위해 내부 필드를 직접 해독할 필요는 없어야 합니다.

## Work 앞뒤의 두 결정

```text
요청서 초안 → 정확한 요청 검토 → 사람이 요청서 수락
                                      ↓
                          시작 기준 → 구현 → 결과 제출
                                                ↓
                              정확한 결과 검토 → 사람이 결과 수락
                                                ↓
                              수락된 결과가 선택됨 → 완료
```

그림은 이 실습의 정상 local 경로입니다. 입력 변경, 검증 실패, 작업 중단이 발생하면 그 지점에서 멈추고 해당 보정·복구 절차를 따릅니다. 리뷰 판정, 테스트 통과, confirmation token은 사람의 결정을 대신할 수 없습니다.

local Work의 적용은 control checkout에 이미 있는 파일에 대한 결정을 기록합니다. linked worker 결과는 별도 적용 절차를 사용하며 이번 실습에서는 다루지 않습니다. Git commit과 push는 두 수락 단계 모두와 별개입니다.

## 화면에서 만날 용어

| 용어 | 이해할 내용 |
| --- | --- |
| 판본(revision) | publish된 작업 요청서나 Work 기록의 정확한 한 버전 |
| 비교 기준(baseline) | Work 결과와 대조할 프로젝트 내용 관측 |
| 결과 명세(manifest) | 변경 전후 내용과 차이의 정확한 메타데이터. 파일 내용의 백업은 아님 |
| 확인 입력(ticket) | 정확한 행동·대상·전제 조건을 묶어 준비한 confirmation 입력 |
| 확인값(confirmation token) | ticket/request에 결속된 값. 사람의 동의를 입증하지는 않음 |
| 결정(decision) | 결과 수락·거부처럼 기록된 사람의 행동 |
| 선택(selection) | 검증된 현재 참조가 가리키는 정확한 판본·결정. 최신 파일명으로 추정하지 않음 |
| 처리 기록(receipt) | 설치·전환·제거를 확인하는 lifecycle 기록 |
| Control checkout | 권위 기록을 쓸 수 있는 primary 프로젝트 위치 |
| Worker | 한정된 실행·제출에 쓰는 별도 linked checkout. control 권위 기록을 쓸 수 없음 |
| 기준 재연결(rebind) | 사람의 승인을 받아 지원 절차로 Work의 baseline이나 intent 연결을 바꾸는 것. ignore 정책 검사를 우회하지는 못함. local Work에서는 새로 수락된 작업 요청서가 필요하며 같은 작업 요청서를 유지하는 rebind는 지원하지 않음 |

“Authority”는 기록의 원본 위치인 `.hrn/`를 뜻하기도 하고, 요청·결과를 수락할 사람의 권한을 뜻하기도 합니다. 디렉터리는 기록을 담을 뿐 agent에게 권한을 부여하지 않습니다.

## 진행을 멈춰야 할 때

| 관측한 상황 | 다음 행동 |
| --- | --- |
| 설치본 없음, runtime 불일치, 지원하지 않는 Git 구조 | 설치 전에 source·interpreter·새 primary 대상을 확인하고 [Getting Started](../../docs/GETTING-STARTED.md) 참고 |
| 초안에 수락을 가로막는 미해결 사항이 있음 | 해결한 새 초안을 publish하고 그 판본을 검토한 뒤 수락 |
| 제출 결과나 필수 문서가 달라짐 | 변경을 보존하고 불일치를 설명한 뒤 지원되는 rework·새 수락·rebind 절차 사용. baseline을 몰래 갱신하지 않음 |
| intent·Work·lifecycle 작업이 pending | 원래 입력과 정확한 source를 보존하고, 다른 쓰기 전에 [Operations](../../docs/OPERATIONS.md) 확인 |
| `status`는 정상이지만 현재 파일이 다름 | Work view와 실제 파일 확인. 과거 완료와 현재 내용은 구별 |
| launcher나 managed 파일이 손상됨 | 상태를 보존하고 [Operations](../../docs/OPERATIONS.md)의 독립 source 진단·repair 경로 사용 |
| 기록을 읽을 수 없거나 알 수 없는 내용·부분 쓰기가 있음 | 보존하고 원인을 확인. 오류를 없애려고 selector를 직접 고치거나 기록을 삭제하지 않음 |

정확한 오류 코드는 [Reference](../../docs/REFERENCE.md), 설치된 제품 없이 보존 자료를 읽는 방법은 [Manual Operation](../../docs/MANUAL-OPERATION.md)을 참고하세요. 확인할 수 없는 관측을 성공으로 바꾸지 않습니다.

## 첫 Work의 기준 유지하기

Colvia는 변경 파일 목록만이 아니라 프로젝트 전체 내용을 비교합니다. ignore 규칙과 범위 밖의 준비는 baseline 전에 마치고, 수정할 Work 설명 문서도 범위에 포함합니다. 테스트 데이터가 결과 내용에 섞이지 않게 두며, 제출 전에 결과 설명을 마칩니다. 필수 참조 문서는 정확한 bytes에 결속됩니다. 이를 변경하면 새 작업 요청서 수락과 rebind가 필요할 수 있으므로 필수 입력을 신중히 선택합니다.

이 경계 덕분에 나중에 agent가 이어가더라도 “무엇을 승인했는가”를 구별할 수 있습니다. 실행 sandbox를 제공하거나 다른 프로세스의 프로젝트 편집을 막는 기능은 아닙니다.

이전 실습의 상세는 [운영 참고 자료](reference.md#과거-설치본으로-진행한-실습)에 있습니다.
