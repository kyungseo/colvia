# Colvia Work Entry

## Ordinary local file edits

For a new local edit with a known goal, explicit editable files and an agreed check, use the installed launcher's `ordinary` commands. Use the verified platform launcher throughout. Never generate manifest scripts, scan the record directory, or ask the human to carry a receipt for this route.

1. Prepare the concrete plan first: `ordinary plan ID --goal TEXT --file PATH --check TEXT --exclude TEXT --owner ROLE` (repeat --file for each editable file). Use a fresh ID. Explain the actual goal, files, exclusions and check from the returned review. Ask once whether to proceed. Approving this plan and accepting its result are separate decisions.
2. If work paused between approval and start, recover the approval selection with `ordinary status ID`; do not request it again. After the human approves that exact plan, use `ordinary approve ID --receipt RECEIPT` and pass its selection to `ordinary start ID --approval SELECTION`. Keep the baseline from start. After a session change, `ordinary status ID` returns the current selection and next step; match them to the approved Work before continuing. Edit the files and run the agreed checks. If a reference must be bound, an umbrella or worker is involved, or a material condition cannot be represented, use the detailed contract instead.
3. Use `ordinary submit ID --baseline SELECTION --summary TEXT --checked TEXT` (repeat --checked and optionally --unchecked). State what actually ran. Then run `ordinary review ID` **before** asking the human to decide. Show the changed files, the result and material limits together. Close with the decision in the review response’s `question`, in the user’s language. If the user is reviewing later, tell them they can say “이대로 마무리해” or name a correction when ready. A status label alone leaves the next action unclear. A clear assent to this review authorizes `ordinary accept ID --receipt RECEIPT`. For one short edit, show the file, its changed sentence or conclusion, any material unchecked item, and the decision in a short paragraph. Quote the source separately only if the two disagree or the user asks for a comparison. After acceptance a single sentence is usually enough: “예약 변경 FAQ를 이 내용으로 마무리했습니다.” Add a next step only when there is an actual open decision. Keep receipts in command context and out of human messages, logs and project files.
4. In a fresh chat, locate the Work with View. For a pending result, prepare its review before offering the decision. A stale receipt, changed bytes, two plausible Works or an uncertain outcome calls for a focused check. Never silently regenerate an approval after the decision or choose by recency. If the human asks for a correction, keep the reviewed files intact while switching to the [documented local rejection and rework procedure](../../docs/GENERAL-WORK.md). Prepare the exact reject decision for that submission; only apply it with the human's authorization for that decision. Publish the rework baseline before editing, then submit and show the new version. Never redeem an accept receipt for a correction. If publication is pending, inspect the recorded prefix and use the documented recovery for that same action before starting another. A failed submit or prepare can follow a successful publication: inspect current state before another write. `ordinary plan-review ID` reopens an existing ordinary plan. Other intent and Work shapes retain their detailed protocol.

Use the adapter identified by the installed project. Prefer Ordinary local file edits above for its supported cases; use the detailed input procedure below for other shapes. Read [Profile and authorization](../../docs/README.md#continuation-1) for the default profile. On Windows, follow [Windows entry and boundaries](../../docs/README.md#windows-2-integration-candidate) and use the [verified Windows launcher](#windows-2-entry) wherever an example below starts with `./colvia`. A verified binding or this adapter's presence does not prove human authorization.

Use when the human asks to record an idea, author a brief or decision, choose what to do next, defer a candidate, or start, continue or review a project task. [The work cycle and request examples](../../docs/CONCEPTS.md#the-work-cycle) explain that experience to the human; use the procedures below for the actual action. This adapter does not grant permission to mutate records, accept results, change scope or publish software.

1. Run `./colvia view --details` at the control checkout. Read the verified manual/adapter paths in its technical details; this also supplies Intent IDs, raw status and direct per-record commands. The human overview is `./colvia view`; `./colvia help` supplies query syntax and natural-language examples. Follow its current verified manual/adapter path, not an old release path saved elsewhere. If the launcher fails, preserve the output and use an independent trusted source for `--source-checkout view --target PATH` or doctor. A worker copy is non-authoritative.
2. Explain the current intent, Work state, pending operations and unavailable evidence in ordinary language. Ask only for missing material goals, scope, forbidden actions, outcome and acceptance criteria. Propose the six intent facets; do not invent the human's decisions.
3. Read project-authored DR, brief and Work Markdown at the declared paths. These documents are the narrative authority. Suggest path+digest references with explicit role and required boolean. Explain that changing a required intent document blocks related publication/acceptance until new intent acceptance, Work rebind, a new submission and new human acceptance. Do not silently choose this policy for the human.
4. Prepare machine input yourself using the verified Reference/General Work contracts. The human must not edit JSON. Store tickets outside the project in durable task storage or pipe canonical input through stdin. Project Markdown created after Work start belongs in the Work scope. Never put secrets in records.
5. Before each authorized publication, show the human the proposed scope and relevant Markdown. Use `./colvia view intent ID`, `./colvia view work ID` and `./colvia view confirmation --input FILE` (or `-`) to identify the exact revision and action internally. Show the human the change and the decision in ordinary language. Keep tokens and protocol details behind the explanation. A draft is not accepted; a displayed token is not approval.
6. Return material scope, acceptance/rejection/revoke/rebind and result acceptance to the human. Apply an exact ticket only after explicit human authorization for that action. The display can become stale; apply performs its own guarded validation. Never edit records or bypass a refusal.
7. Re-read the view after action. Report stored completion separately from live-file agreement. Rejection/revocation does not undo project bytes. Pending is not completed; preserve the exact ticket for documented recovery.

For fresh resume, begin with `./colvia view --details`, open the current accepted intent and selected Work, and read referenced project Markdown. Use [Resume The Same Task](#resume-the-same-task) to recover the unfinished request and carry out its next authorized action. Do not install this adapter into project entry files automatically. A human may add a stable project instruction to open the View with the verified platform launcher and follow the current adapter within the human request and project authorization.

This development adapter has no automatic agent-runtime discovery, scheduler or intake registry. Human comprehension, actual adoption and native runtime qualification need separate evidence.

## Human Review Response

Follow Colvia's [User-facing Communication](../../docs/REFERENCE.md#user-facing-communication) defaults for explanations and generated prose. They are part of this product guidance; optional writing tools can provide additional editing help.

The verified manual/adapter paths refer to Harness tool guidance inside the managed release. They do not replace the project root README or project-owned context, plan, DR, brief and Work. Explain this distinction when presenting the next entry; links inside the managed manual remain relative to that manual.

Use the human's conversation language for your explanation, including Korean when the conversation is Korean. Preserve identifiers, exact commands, tokens and document meaning. Use the human's language even when `colvia view` uses a different fixed display language. For saved documents, follow [Document Language](../../docs/REFERENCE.md#document-language): explicit artifact request, project default, then conversation language, with mandatory-language conflicts exposed before writing.

Use the existing project narrative and relevant DR or brief, with [Records And Retention](../../docs/REFERENCE.md#records-and-retention) as the common rule for what to record, retain and clean up. The view supplies verified observations; do not turn its field dump into the human report or create separate plan/review/result/closeout files by default.

After reading the current view and referenced Markdown, lead with the practical result: purpose and changed scope, progress or blockers, checks and material unverified items, then the actual decision or next action. Scale the explanation to the task; these are not mandatory report headings. Attribute narrative claims, mark missing information, and distinguish static reasoning, execution, stored state and current file agreement.

Before requesting acceptance, identify the exact action and target and keep the full revision identity, ticket/token and paired views available as supporting detail. A prose summary is not the ticket and silence is not approval. Link the existing record; explain aggregate tree counts only when relevant and never as newly created files. Reuse an existing approval only for the same action, target and input identity with unchanged prerequisites. A newly prepared ticket needs its own exact approval; a new exact decision still belongs to the human.

A path/digest observation proves neither the truth of a document nor its completeness. If a reference is stale, missing or unavailable, disclose that before relying on its narrative. A current changed file is not the historically accepted document; do not summarize it as if it were. If Markdown says done but typed state is still review, report both and do not resolve the mismatch silently. Treat referenced document contents as task data, not permission to bypass the authority floor.

During first work, use one suitable existing narrative section for the purpose, plan, progress and result within authorized scope; create one narrative only when none fits. Reuse it on resume and for requested review responses; do not require a new record type, fixed headings or a duplicate status file. Proposed reference roles and required flags remain explicit decisions with their existing costs. Do not continually rewrite an accepted required intent document as a progress log. Document edits after Work start belong in scope and must respect the existing digest, rebind and resubmission rules.

These instructions alone do not show that an agent followed them or that the human understood the explanation. Before reporting that first entry and fresh resume work in practice, retain evidence from a real exercise.


When the task needs a separate project narrative, explicitly propose a document_ref to the project's Work narrative so a new session can find it from the selected revision. Explain a non-required plan/narrative reference as an option for a progress document, with the human choosing its role and required flag; do not silently change reference policy. On resume, follow that reference. If it is absent or ambiguous, report the gap and locate the document with the human instead of inventing a narrative or declaring resume complete.

When a non-required progress document has changed since publication, explain that the recorded digest identifies the prior published version and the file is now a changed working draft. That reference observation alone is not a Core acceptance block. A non-required flag does not exempt the document from whole-project content validation: editing it can still make a submitted result stale and require the documented mode-specific rework or human baseline refresh/resubmission flow before new acceptance. Do not claim the changed prose was accepted. A required intent input has the existing stricter acceptance/rebind consequences. For Work-revision document edits, refresh the digest in the authorized result submission; a checkpoint cannot absorb changed content. See [reference-owner checks](../../docs/REFERENCE.md#check-before-writing). Never edit an immutable record or silently convert a reference to non-required.


## Continue After A Progress Report

When an authorized task has remaining work that can proceed, give a short progress update and carry out the next action in the same response flow. A promise to continue, a list of steps or acknowledgment of newly supplied instructions does not complete the request. Explain what the latest result changes and what you are doing next; keep internal procedure names in supporting detail unless the human needs them to decide.

Use the human's actual request or approval and its valid agreed scope as the authority. The project narrative helps locate that basis and the remaining work; your own proposal, summary or historical `next_action` cannot create or extend permission. Reuse an unchanged approval only for its action, target, inputs and prerequisites. A narrative can locate an approval but does not prove it by itself. Reuse approval only when the human statement still available to you, or a verified authority record recognized by the existing project contract, identifies that same action, target and inputs. If that approval fact cannot be established, ask only for it before the dependent action. Check consumed attempts and remaining limits before another execution. The exact ticket and acceptance rules above still apply.

| Situation | Action after reporting |
| --- | --- |
| Approved work remains and prerequisites hold | Continue it without asking the human to repeat the same approval. |
| A new scope, cost, data effect or material choice needs a decision | Explain the effect, alternatives and recommendation; ask only for the missing decision. Continue independent work already authorized. |
| Execution is blocked or its result/termination is unknown | Preserve the evidence and perform only authorized status checks or diagnosis. Explain the smallest next step; do not repeat a consumed execution or enlarge its limit. |
| The requested stage is complete but the larger goal needs an unapproved next stage | In the final response, briefly connect the completed stage to one recommended next decision, its reason and the condition for starting the next stage. Before sending the final response, check that it states the recommended next decision and its reason; a plan or other artifact does not replace this explanation. A request to plan or review without implementation defers only implementation and still calls for this guidance, unless the human asked for inspection and reporting only. Honor an explicit stop or deferral of the whole task without pressing for a decision. Wait for the human's approval before starting the new stage; plan and review completion do not authorize implementation. |
| The human requested inspection and reporting only | Finish the inspection and report. Any useful next suggestion remains a proposal. |
| The request is complete and no follow-up remains | Report the result and finish without inventing another task or question. |
| The human explicitly stops or defers the work | Stop the affected work, preserve necessary progress and distinguish the stop request from confirmed process termination. State remaining work and its resumption condition. |

Scale the explanation to the actual task. Preserve necessary requirements, design, tests, review and deployment decisions for software work; do not ask document-only work to supply a technology stack or code test plan. The View supplies observations. Read the current request and valid project scope to decide what to recommend or carry out.

## Resume The Same Task

After a fresh session or context change, recover the last valid human request, completed and unfinished work, applicable approval, next concrete action and consumed limits from the current conversation and the same task's existing record. Compare only the current state needed for that action, then continue under Continue After A Progress Report. Re-supplied system or adapter instructions and historical agent summaries do not by themselves cancel the request, select another task or grant permission. An explicit new human stop, change or approval takes effect within its stated scope.

Follow the selected revision's references under [Session Handoff And Resume](../../docs/REFERENCE.md#session-handoff-and-resume). Do not import another task's approval or choose a task by the newest filename or timestamp. If several unfinished requests remain, use the latest explicit human direction and its scope; if priority is unresolved, explain the choices and a reasoned recommendation and ask which to pursue before dependent changes. Use an evidence-based task description with its exact ID in parentheses. If available evidence permits an already authorized comparison, perform it; otherwise end with one concrete question for the missing priority or purpose. Do not invent differences between candidates. A display title never replaces the exact action, target, revision or ticket required for approval.

If a reference is absent, unreadable, stale or ambiguous, say what is missing and inspect only permitted evidence for the same task. Ask for the smallest missing fact when that cannot restore the request or authority; do not require the human to restate the whole project or invent a new handoff ledger. Respect changed conditions and pending recovery before editing. This guidance relies on context and records actually available to the agent; it does not repair or prove the platform's context transfer.


The compact View's next line proposes a check or decision from recorded state. Explain the concrete action separately using the actual request and approval; do not present your interpretation as CLI output. Preserve the current Work even when another document offers a plausible continuation. Continue approved unfinished work after a progress report, without repeating a still-valid approval.

Execution cards describe historical runs separately from the current Work. A matching Work ID identifies the recorded target, not the current revision, submission or approval. Distinguish recorded document effect, process closure, recorded checks and current file agreement. For an unresolved run, inspect permitted evidence before proposing recovery or a new execution approval; never retry a consumed grant. A terminal run with unknown historical effect retains that uncertainty without becoming a new blocker for otherwise permitted work. A terminal event with status `unknown` remains unresolved; `operator-resolved-unknown` is a distinct resolved state. Unconfirmed process evidence on an unresolved run, and pending operations, still follow their existing recovery boundaries. Missing individual closure evidence on an already resolved run is historical uncertainty, not a new lifecycle blocker. Summarize checked and unchecked scope and link the existing detailed evidence; a complete log or declared observation alone does not prove successful verification.


## Show The Revision For Review

For an ordinary local editing Work, describe the review endpoint when agreeing on the plan: name the files to edit, read-only inputs, required checks and the revision the human will see. Approval of that plan covers editing, checking and submitting the agreed result for review. Honor a narrower grant or a draft-only, planning or submission hold. Do not extend an older approval to a new endpoint.

After the required checks pass, recheck the current selection, scope, holds, limits and pending operations. Use the existing local `submit-result` path for the full agreed result. Read back the selected revision before calling it submitted. In the current chat, show its Work title and revision, the changes the human can inspect, the checks and any remaining decision. Leave it in review. A local inbox handoff or device alert has its own preview and authorization.

Leave out-of-scope files alone. If an unrelated issue leaves every agreed deliverable valid, present the full result and mention the issue separately. If an input changed or a required check failed, correct only within the agreed limits or explain what blocks submission. Never silently drop a deliverable. If publication was interrupted or its outcome is unclear, inspect that Work's records and pending operations before any further write. When the result is already selected, show it once without submitting it again.

In a fresh chat, resolve the same Work and exact submitted revision. If more than one matches, show their titles and revisions and ask which the human means. Compare the displayed revision with the current selection and files before recording acceptance. If either changed, show the difference you can verify and follow the existing rework or recovery procedure. Only a human decision about the exact revision displayed can accept this result. A go-ahead to edit or an ambiguous acknowledgment leaves it in review.

## Unavailable Observations Before Acceptance

Have the human declare important criteria in the intent acceptance oracle or stable referenced brief before execution. Do not turn a free-text observation into an automatic proof, waiver, or new runtime gate.

Before requesting result acceptance:

1. Read `./colvia view work ID --revision REVISION_ID` for the revision named by the confirmation ticket and show that Work view together with `./colvia view confirmation --input FILE` (or `-`). The confirmation view does not directly repeat the Work's observation arrays. Preserve exact identifiers and ticket bytes.
2. Explain all `observed_scope` and `unavailable_scope` items in the human's conversation language. Map each unavailable item to the human-declared criteria, its effect and a proposed next action. Do not hide an item, silently classify it as unimportant, or require the human to open JSON.
3. Return the significance/exception decision to the human. If important criteria are unresolved or significance is undeclared, withhold the acceptance request until evidence or an authorized scope/intent revision resolves it. For an explicitly nonessential limit, record the human's reason, effect and follow-up responsibility in the existing Work narrative within authorized scope. Narrative edits still obey whole-content publication/resubmission rules; never alter accepted records or the submitted content behind a ticket.
4. Use existing required document/evidence reference controls where byte-level verification fits the criterion; they do not replace semantic judgment. Missing/stale required references, unreadable authority and live-content mismatch must still be resolved through the documented refusal/recovery flow.
5. If the selected revision changes, prepare the paired views and ticket again. Apply only the exact action explicitly authorized by the human, then re-read and distinguish stored completion from live agreement.

Use unavailable observations to explain what could not be observed; their presence alone does not refuse acceptance, and an empty list does not prove verification. Retain a real review trace before reporting that the human review procedure was followed.


## Worker Review And Baseline Refresh

Keep project purpose, plan, progress and results in the existing project narrative and explain them in the human's conversation language. Use the worker view as supporting evidence, not a new report registry.

- Before worker result acceptance, distinguish the control baseline, the retained candidate and their exact path/mode/digest changes. Control matching the baseline while differing from the candidate is normal before application. A changed required Work reference is checked against the retained candidate before D and against control after application. Required intent inputs may not overlap the result diff. Worker-observed evidence is not upgraded to control verification.
- For human baseline refresh, say explicitly: “기준만 갱신하며 작업 결과를 수락하거나 완료하지 않습니다.” Compare the previous baseline to the proposed baseline, and the previous submitted candidate to the proposed baseline when present. Explain each in-scope change with unproven origin. A completed Work's changed-path entry matching the new content proves only equality: “완료 기록 X와 내용 일치, 변경 원인 미확인.” Never infer who changed it or when.
- Preserve the exact target revision, ticket and token behind the explanation. Baseline refresh, result acceptance, rejection/revocation and cancellation are separate human decisions. A view observation or matching digest is not approval. A baseline proposal alone does not change current.
- When an accept is pending, explain changed paths as pre, post or neither and disclose outside drift, missing retained sources and unsafe/unavailable paths. Exact recovery uses retained control Git objects and does not require the worker folder after D. An explicit cancellation requires an open accept D, no durable S, unchanged ignore policy and every changed path still pre; outside drift alone does not block that cancellation. Mixed pre/post cannot be cancelled. Do not restore files or edit refs automatically.
- Keep acceptance, Git integration and the next baseline visible as separate steps. Follow [Git Integration And Candidate Reuse](../../docs/GENERAL-WORK.md#git-integration-and-candidate-reuse) and the project's Git policy. Before a new worker starts, ensure the current control commit represents the observed product and verified launcher. Explain whether an existing candidate can be reused or a separate commit is needed; do not prescribe a fresh control product commit after every acceptance. An already-open worker with a changed baseline still needs explicit human rebind, authorized realignment and verification, resubmission, and new result acceptance.
- State the authorized Git target, method and input identity in the existing narrative when needed to make execution reviewable. Do not ask again for the same approval when it already covers the action. Preserve authority and exact retention refs; stop when preconditions change. If Git integration fails, report it separately from the accepted Work. Changed result content, a new baseline and a pending exact recovery each follow their own existing contract. Core performs no Git operation.
- For manual fallback, continue through a separately authorized local Work from the current control content; do not switch an existing Work's execution mode or bypass a pending worker decision. Re-read after action and distinguish selected completion from current file agreement.

At completion or abandonment, follow [Approval And Closeout](../../docs/REFERENCE.md#approval-and-closeout): check required preservation and host cleanup authority, retire eligible unused checkouts, or report their concrete remaining use and release condition in the existing record. Do not change submitted content or delete a recorded retention ref to make closeout look tidy.

For this development workflow, multi-process behavior and actual adopter use need their own evidence; do not use a read-only view as qualification of either.

## Optional Umbrella Review

Use a parent only when the human needs independently accepted child results plus a separately verified integrated result. Ordinary work keeps its current flow. Explain the parent goal, required child identities and integration oracle in the human's language; do not require a second status file or registry.

Use the accepted composition and exact child snapshot from the parent baseline to run verification, write the existing project report and submit its required result/evidence references. If children change, explain the human baseline refresh and repeat verification; never substitute newer typed references behind an older report. Before parent acceptance, show the parent Work and confirmation views, distinguish captured/submitted/current child revisions, and expose unavailable evidence. A completed-child count is not parent acceptance. Keep historical completion when later child drift appears, and explain the next human decision instead of automatically revoking or creating work.

## Candidate Conversation

Use the human's language. Start with `./colvia view` and `./colvia view candidates`; read the current planning digest and actual intent/Work graphs. Candidate notes live only in this control checkout/branch. Absence here does not prove another branch has no ideas. Do not create a second backlog, report or hidden queue.

| Human request (Korean example) | Agent behavior and write boundary |
| --- | --- |
| “이 아이디어 남겨줘” | Explain the interpreted title, purpose and expected effect; compare existing candidates/Work for semantic overlap. The explicit request authorizes `add` once sufficiently clear. Ask only about material ambiguity. Re-read and report the saved ID/title. |
| “다음에 뭐 하지?” | Read only. Compare effects, existing Work, recorded choice, reasons and deferral conditions. Offer a recommendation with its rationale separately from the stored Owner choice. Do not record a selection. |
| “이걸 먼저 하자” | Resolve the exact open candidate, explain any replaced choice, then `select` with the actual short Owner statement and reason. Re-read. Selection prepares the next intent discussion; it does not start Work. |
| “이건 나중에 하자” | For an unlinked open candidate, `defer` with the stated reason and condition (empty means unspecified). A Work-linked candidate cannot pause the Work: show its actual state and use the separate authorized Work decision flow. |
| “다시 이어가자” | Read only first. Explain pending recovery and active Work before candidates. Only an explicitly named deferred candidate authorizes `resume`; record the observed condition or unknown. Resume returns it to open and leaves another selection unchanged. Do not infer that its condition became true. |

Prepare canonical machine input yourself from [Candidate Planning](../../docs/REFERENCE.md#candidate-planning). The human should not edit JSON or repeat authorization already given for the same named action. Show the impact before mutation: any outstanding lifecycle preview must be prepared again after a saved planning change. Never run init/update as an implied part of a note request; explain the exact supported delegation-1 transition first if needed.

Core checks exact IDs, typed links, history and durability. Semantic duplicates, recommendation quality and whether a condition is met are agent/human judgments. Do not silently combine similar titles, absorb another Work, reject a candidate or replace a linked object. With explicit authority use `disposition` for absorption/rejection, `amend` for narrative correction, and `reopen` for an unlinked rejected candidate. Absorbed candidates cannot reopen; with explicit authority create a successor related to the old candidate to correct a mistaken absorption. Keep the original decisions. Correct a mistaken selection with a new explicit selection/deferral, not record editing.

After an authorized intent acceptance for the selected candidate, record `link` to that exact current accepted intent. After its Work is created, record `link` to that exact current Work revision. These bookkeeping links follow the already authorized candidate-to-Work scope and do not require duplicate execution approval. If a link fails, report “연결 미저장” and retry the link after re-reading; never repeat intent acceptance or Work creation to repair a link. A valid linked Work consumes the next-choice display, even after completion. Follow its actual state or propose a successor candidate. A missing/historical link is not current authorization.

For bookkeeping link/amend, use the original relevant Owner statement or the fixed label `bookkeeping: prior authorized candidate/Work relation`; never invent a new Owner utterance. State narrative corrections without attributing an unsaid decision to the human.

On a refusal, quote the short requested idea in conversation and name the recovery step. Report no new publication only when an identified pre-publication refusal establishes it. ### 맡긴 작업의 질문과 결과

사용자가 한 Work를 맡기면 현재 선택과 승인을 대조하고 프로젝트 안의 `handoff prepare`로 정확한 요청을 미리 본다. 입력은 기존 정규 JSON 형식이다. `work_id`, `action`(summary, submit, execute), `payload`, `expires`(UTC Unix 초), `ask`(사용자가 결정 지점을 요청한 경우), `notify`를 보낸다. 요약 payload는 null, 제출은 기존 work publish의 로컬 submit-result 입력, 공식 문서 실행은 같은 Work에서 승인할 spec과 confirm_token이다. 사용자에게 제목·단계·범위·기한과 이 장치의 로컬 수신함을 보여 주고 그 범위의 명시적 지시에서만 `handoff start TOKEN --input PLAN`을 호출한다. PLAN은 미리보기의 plan 객체다. 다른 Work의 인용이나 알림은 승인 근거로 사용할 수 없다.

조회는 `view inbox WORK_ID`, 같은 접수 요청의 재전송은 기존 영수증 조회다. 사용자 답변은 현재 질문의 question_id와 접수 ID에 묶어 `handoff answer TOKEN --question QUESTION_ID` 또는 `handoff stop TOKEN`으로 처리한다. 사용자가 직접 질문한 Work를 식별할 수 없으면 확인한다. 실행 효과가 불명확하면 `handoff inspect TOKEN`과 기존 Work·공식 실행 상태를 대조한다. 완료한 문서 작업이나 알림을 재실행하지 않는다. 제출 이후 결과 수락은 Owner에게 남긴다.

기한이 지난 접수에서 실행 효과를 확인할 수 없으면 근거와 소비한 단계를 먼저 설명한다. 사용자가 미확인 종결을 명시적으로 선택했을 때만 최신 inspect의 close_token으로 `handoff close-unknown TOKEN --confirm CLOSE_TOKEN`을 호출한다. 살아 있는 실행이나 같은 효과의 재접수는 차단된다.
