# DR-0008: Development Record And Documentation Checkpoints

## Question

Where should Colvia record developments that affect progress, public and installed documentation, or the verification of release guidance?

## State And Scope

Named amendment to [DR-0003](DR-0003-source-development-procedure-and-bounded-intake.md). [DR-0006](DR-0006-source-contributor-document-structure.md) identifies the source workflow and its authority. The [acceptance and activation record](#acceptance-and-activation) identifies the exact effective revisions, accepted scope and date.

This is a source-development procedure for contributors and maintainers. The proposed directions apply to equivalent project and platform conditions. Use public-safe examples in shared documents and preserve private observations with their existing evidence and runbooks. See the [owning development record](../development/CHORE-20261117-003-development-record-and-documentation-checkpoints.md) for local preparation and verification.

## Decision

Adopt the named checkpoints and affected-guidance checks at the exact revisions recorded below. Use the existing owning record and release procedure for their results.

## Rationale

The same task record can expose missed guidance and verification at the points where a contributor already plans, resumes, closes or prepares a release.

## Consequences

Contributors check the affected guidance and evidence. Maintainers keep host-specific procedures with the relevant runbook and observations.

## Options Considered

- Keep the changes in individual task records. This preserves their details, with recurring checks left to each task.
- Put shared checks at the existing workflow and guide entry points. This makes the next task find the right checks and keeps host-specific recovery in its operational runbook.
- Add a new universal registry and checklist. This adds a second progress surface and increases the effort for small source-only edits.

The proposed amendment uses the second option.

## Evidence And Promotion Conditions

Validate three existing cases against the proposed checks: a source-only documentation edit, a guide change that alters the ZIP contents, and a Windows support claim that depends on an exact host and artifact. Include the unrelated scope check and a broader Windows claim as counterexamples, and assess this proposal as source-only guidance. Reuse the affected manual, package and device-test evidence for those checks. Keep limitations visible. Use the existing plan and result review procedure. Before activation, record the Owner's explicit decision on the exact amendment, source revisions, affected clauses and effective date.
