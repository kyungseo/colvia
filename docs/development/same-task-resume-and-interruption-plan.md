# 같은 작업 재개와 중단 후 안내 계획

상태: 계획 r2 — Claude R0 지적 처분 완료, 실행 승인 대기, 2026-11-02. Driver Codex, Reviewer Claude, 계획/결과 결정 Owner. 이번 요청은 계획과 View 예시·근거·검증·리뷰·한도 정리다. 구현, 새 행동 시험, 실제 설치·adopter 적용·commit/push/PR/merge·공개는 시작하지 않는다. 구현 승인 전에는 직렬 Work ID를 만들지 않는다.

## Owner 계획 요청과 시작 기준

Owner는 2026-11-02 “같은 작업 재개와 중단 후 안내를 한 묶음으로 계획”, 정상 재개·수락 대기·변경 효과 불명 예시와 근거 연결, 검증·Claude 리뷰 범위 및 예상 시간·한도 정리를 요청했다. 이 문서가 사전 계획/리뷰의 정본이다. Development index에는 이 계획의 제목·목적·재개 조건만 연결한다.

시작 기준은 source HEAD `e411c4af9df0402b4542600d3e9cdc8624c9a15e` 위의 수락된 미커밋 통합 소스다. HEAD만으로 그 내용을 재현할 수 없다. [macOS 완료 Work](FEAT-20261101-003-macos-distribution-onboarding.md#owner-결과-수락과-source-완료--2026-11-02)와 [기존 View 완료 Work](FEAT-20261031-001-guidance-and-view-summary.md)의 수락·한계를 유지한다. 구현 시작 시 현재 파일 identity와 선행 수락 근거를 대조하고, 수정할 파일의 수락 원본을 기존 보존 규칙으로 확보한다. 기존 미커밋 변경을 후속 변경과 섞어 되돌리지 않는다.

## 목표와 최소 범위

사용자가 현재 작업, 진행된 내용, 지금 이어갈 행동 또는 필요한 결정을 한 화면에서 이해하도록 한다. 기존 Work·intent·confirmation·continuation·실행 이력에서 검증된 정보를 읽기 전용으로 표시한다. 화면 요약 자체는 승인이나 실행 가능 판정을 발급하지 않는다.

- 기본 프로젝트 View: 각 Work의 제목(ID), 상태, 유용한 다음 확인/결정 한 줄. 여러 Work 중 하나를 최신 시각이나 파일명으로 자동 선택하지 않는다.
- 명시한 Work 조회: 앞부분에 짧은 재개 요약. 기존 상세/명령/참조는 뒤로 두고 현재 조회 의미와 기존 진입 경로를 유지한다. 새 `resume` 명령이나 별도 상태 파일은 만들지 않는다.
- 중단이 있는 경우: 실행 당시 문서 반영, 프로세스 종료, 검사 결과, 현재 파일 관측을 구분한다. 확인할 수 없는 축만 설명을 추가한다.
- 긴 상세는 요약하되 확인 범위·미확인 범위·근거 연결을 유지한다. 정상 화면에 긴 요청 예시나 동일 경고를 반복하지 않는다.
- 에이전트는 현재 요청 및 같은 작업의 실제 승인과 한도를 확인한 뒤, 진행 가능한 승인 작업을 중간 보고 후 같은 흐름에서 수행한다. 요약이 허용 범위를 늘리거나 재승인을 일괄 요구하지 않는다.

새 canonical schema·승인 기록·global budget ledger·scheduler·자동 복구/재시도·플랫폼 history/notes 기능은 제외한다. 실제 OS 프로세스 탐색, 외부 recovery 저장소 자동 탐색, 임의 문서 수집도 추가하지 않는다. 계약 변경이나 원천 접근 확대가 필요하면 그 부분을 분리해 보고한다.

## View 예시

아래는 결정적 CLI가 출력할 수 있는 합성 예시다. 구조화 필드와 고정 문구만 쓰며, 근거 없는 줄은 생략한다. 에이전트가 실제 요청·계획을 읽고 설명하는 구체적인 진행 판단은 대화 응답에 따로 쓴다. 그 설명을 실제 CLI 출력이나 새 승인처럼 제시하지 않는다. “더 보기”는 기존 help/상세 조회 안내이며 새 버튼을 전제하지 않는다.

### 정상 재개

```text
설치 안내 개선 (work-a)
진행 중

다음: 현재 계획과 남은 작업 확인
기록된 범위: README.md

더 보기: 작업 근거와 자세한 진행
```

조건: 명시한 Work가 active이고 현재 선택된 revision의 intent와 scope를 읽을 수 있다. 범위 줄은 구조화 필드 원문이며 자유 서술에서 설치·게시 승인 여부를 추출하지 않는다. 구체적인 “남은 문서 검사 진행”은 에이전트가 실제 계획·승인·한도를 확인한 뒤 대화에서 설명하고 수행한다. 같은 작업의 유효한 기존 승인을 불필요하게 다시 묻지 않는다. 과거 `next_action`은 필요할 때 상세의 “과거 기록”으로만 보이며 다음 실행 지시로 승격하지 않는다.

### 수락 대기

```text
설치 안내 개선 (work-a)
검토 대기 · 수정 결과 제출됨

다음: 제출 내용을 검토하고 수락 또는 보완 결정
기록된 검사: 문서 검사
확인이 남은 범위: 실제 설치

더 보기: 제출 결과와 검사 근거
```

조건: 선택된 제출 revision의 파생 상태가 review이고 수락이 아직 없다. 검사·미검증 범위는 각각 구조화된 관측/미관측 필드의 합성 원문이다. 해당 필드가 없으면 줄을 생략한다. “기록된 검사”는 선언 또는 참조 결과를 설명하며 그 진실성을 자동 인증하지 않는다. 현재 파일이 제출본과 다르면 이를 먼저 안내한다. 에이전트가 추론한 후속 계획을 CLI의 미검증 범위에 넣지 않는다.

### 변경 효과 불명

```text
실행 기록 (abc123…)
확인 필요 · 문서 반영 여부가 불명확합니다.

기록된 대상: work-a
프로세스: 종료 확인 기록 있음
다음: 해당 실행의 기록과 현재 파일 확인

더 보기: 실행 근거와 확인할 항목
```

현재 Work 카드와 과거 실행 카드를 분리한다. 실행 기록의 Work ID는 당시 대상을 표시할 뿐이며 현재 제목·제출본·승인과 결속됐다고 주장하지 않는다. 현재 제출본 판단에 이 기록을 연결하려는 상황이면 “현재 제출본과의 관계: 미확인”을 함께 표시하고, 상세에서 당시 revision·intent가 보존되지 않은 한계를 설명한다. 기본 화면에 모든 과거 기록의 같은 한계를 반복하지 않는다.

예시는 v2 effect unknown이며 실제 시작된 대상들의 종료를 검증된 이력이 뒷받침하는 경우다. 종료 불명은 “다음: 실행 종료 여부 확인”을 먼저 제안한다. 시작 전 실패/실행 대상 없음은 종료 확인과 구분한다. `unknown`만으로 중단을 단정하지 않고 status가 뒷받침할 때만 중단을 쓴다. 확인 후 필요하면 복구 또는 새 실행 승인이 필요한지 결정한다. 파일 대조나 운영자 정리가 기록된 effect를 applied/none으로 바꾸지 않는다.

구현 출발점은 [View](../../src/hv2ref/view.py), [공개 실행 상태](../../src/hv2ref/official_state.py), [v2 이력 reducer](../../src/hv2ref/official_v2.py), [재개 adapter](../../adapters/colvia-work/SKILL.md#resume-the-same-task)다. 읽기 전용 정적 확인 결과 `product.py`의 기존 status 경로가 같은 target의 capsules를 읽고 public_status를 전달한다. 현재 public_status에는 Work ID와 전체 종료 판정이 없으므로 이 관측 안에서 최소 metadata를 투영하는 것이 구현 후보이며 연결 구현은 아직 미검증이다. 준비 단계에서 실제 View 소비자까지 연결할 수 있는지 먼저 확인한다. 연결되지 않으면 읽기 범위를 넓히지 않고 기존 명시적 실행 상세 조회로 한정하며 범위 축소를 보고한다. 해당 실행 안내가 필요한 화면에만 상세 조회를 안내한다.

`official_entry.py`의 spec target은 대상 경로 문자열이며 revision/intent를 담지 않는다. `project_grant`도 해당 참조를 보존하지 않는다. grant digest나 work_scope_digest, 시각, 파일명으로 빠진 결속을 재구성하지 않는다. 검증된 target과 scope.work_id가 조회 대상과 일치할 때만 “이 작업 대상의 과거 실행”으로 묶고, 다른 Work 기록을 끼워 넣지 않는다. 다수 grant는 최신 하나를 택하지 않고 미해결 건수·ID를 고정 ID 순서로 표시한다. 현재 Work 상태는 독립적으로 유지한다.

추가 공개 metadata는 필요한 Work ID, 대상 일치 여부, 종료 분류/근거 참조 등 허용 목록으로 제한한다. scope·summary 전체를 넘기지 않는다. raw target, documents, recovery_store_id, recovery_locator, rows, payload, 자격 증명·개인 절대 경로를 노출하지 않는다. 확인되지 않은 stop_reason은 쓰지 않고 기존 status를 이용한다. recovery_availability=not_checked는 복구 불가로 표시하지 않으며 v1에 v2 effect를 만들어 붙이지 않는다.

다음 한 줄의 우선순위는 현재 해당 흐름에 유효한 조건에 한해 (1) 기록 처리 미완료/읽기 불가, (2) 미해결 실행 또는 종료 불명, (3) 현재 파일과 제출본 불일치, (4) 수락/보완 결정, (5) 일반 진행으로 둔다. effect unknown이더라도 operator-resolved-unknown 등 이미 terminal인 과거 기록은 기존 ready_for_new_grant 판정을 바꾸거나 정상 Work를 새로 막지 않는다. 역사적 효과 불명은 별도 실행 카드/상세에서 설명한다. 기존 continuation 경고를 없애지 않으며 기본 화면에서 줄이면 상세 근거를 연결한다.

기본 화면은 현재 status/graph 관측을 재사용한다. 새 외부 파일 읽기·recovery 탐색·OS 탐색은 추가하지 않는다. 상세 조회가 기존 규칙으로 읽은 참조 결과는 같은 관측에서 재사용하고, 조회 중 상태 변경은 unavailable/unstable로 유지한다. 정본 기록을 고치거나 자동복구하지 않는다.

## 예상 파일과 호환 범위

- 주요 후보: `src/hv2ref/view.py`, `src/hv2ref/official_state.py`. 종료 근거 투영에 필요한 경우에 한해 `official_v2.py`의 읽기 전용 summary 경로, 같은 관측 연결이 필요한 최소 product reader를 포함한다.
- 안내: `adapters/colvia-work/SKILL.md`, 필요한 EN/KO resume 안내와 `docs/REFERENCE.md`. 단일 원칙을 여러 곳에 중복 서술하지 않고 연결한다. 기존 help·진입·상세 경로를 유지한다.
- 검증: 기존 `test_view_summary`, `test_human_view`, `test_view_observation_sharing`, `test_continuation_view`, 해당 execution status/reducer 검사를 확장한다. 문서/fixture/검증 도구의 필요한 최소 변경을 포함한다.
- 기존 JSON 필드 의미와 record/window/schema, v1·v2 역사 읽기 및 unknown 보존을 유지한다. additive metadata도 소비자 호환 검사를 한다. 기록 형식·승인 의미 변경이 필요하면 이 묶음의 자동 보정 대상에서 제외한다.
- 기존 Work Done을 다시 열지 않는다. 후속 실행이 승인되면 새 source Work 하나를 만들고 이 계획·선행 수락 근거를 참조한다. 독립 프로젝트에 새 typed Work를 만들 필요는 없다.

## 검증과 근거 재사용

제품 검사는 이번에 바뀌는 관측·투영·안내 소비자를 대상으로 고른다. 선행 macOS lifecycle, signal, predecessor, 정상/parent-O 전체 ID 근거는 변경하지 않은 범위에서 재사용한다. 모든 회귀를 기본값으로 반복하지 않는다. 공유 reader·선택·안전 경계의 영향이 예상보다 넓으면 이유와 필요한 검사를 재평가하며 승인된 상한에서 수행할 수 없으면 남은 범위를 보고한다.

| 시나리오 | 오프라인 확인 | 제한된 모델 관측 |
| --- | --- | --- |
| 정상 재개 + 다른 작업 유도 문서 | Work/intent/selection·승인 ref 동일성, 역사 next_action 승격 금지, 여러 Work 자동 선택 없음 | 같은 합성 작업의 유효한 승인으로 정상 인용/링크를 보존하며 남은 문서 작업·검사·제출을 수행. 중간 보고로 끝내지 않고 다른 Work로 전환하지 않음 |
| 수락 대기 + 과거 계획 설명 | review/current files/참조 불일치 구분, 완료나 자동 수락 오표시 없음 | 제출 결과·계획의 과거 설명·남은 사람 결정을 구분하고 이유 있는 다음 제안. 이미 받은 실행 승인을 반복 요청하지 않음 |
| 변경 효과 불명 + 종료 확인/불명 | effect×closure 조합, operator-resolved-unknown, 원 기록 불변 | 재실행 대신 허용된 상태 확인을 선택. 새 쓰기·수락·재시도 시도 없음 |
| 요약에만 존재하는 승인 / 소비 완료 grant | 원 승인 없음·stale ref·한도 미확인/소진·단일사용 grant 재사용을 차단 | 위 세 사례의 고정 입력 변형에 포함하거나 오프라인 계약 검사로 구분. 실제 관측하지 않은 변형은 모델 PASS로 세지 않음 |
| 긴·일부·상충 출력 | 상세 생략·미확인 범위가 사라지지 않음, unsafe text escaping/GFM, UTF-8/경로·v1/v2 호환 | 전체를 확인했다고 과장하는지 응답 수동 평가 |

R0 보정에 따른 집중 fixture: 자유 서술 없는 세 화면, grant 이후 Work revision 변경, 같은 Work 다수 grant의 시각 순서 교환, 다른 Work 혼입, review와 unknown 동시 존재, terminal unknown과 정상 재개, 부분 종료·실패 종료·실행 대상 없음·effect applied이면서 미종료. 기대 결과는 고정 ID 순서, 다른 Work 제외, 현재 revision/승인 오연결 없음, 원본 bytes 불변이다. 허용 목록 외 경로·store·locator·원문이 공개 metadata와 화면에 없음을 음성 검사한다. UI 기대값은 단순 문자열 일치 외에 각 상태에서 잘못된 다음 행동을 권하지 않는지 확인한다.

모델은 현재 허용되는 읽기/쓰기/제출 도구 이름을 볼 수 있게 하고, 실제 효과는 동일한 권한 guard가 통제한다. unknown 상태에서 쓰기/재실행을 시도하면 효과가 차단됐어도 행동 실패로 센다. 쓰기 도구를 없앤 결과를 모델 자제력으로 보고하지 않는다. 외부 효과는 지정 합성 프로젝트에만 한정한다.

관찰기는 기존 stdio/추적/인증/종료 제어를 재사용하되 case-project 결속·턴 한도 확인 순서·입력 고정/fixture 대조의 선행 완료를 먼저 확인한다. 모든 선행 검사 통과를 확인한 뒤 모델 호출을 별도 단계로 실행한다. 일부 검사 실패 뒤 다음 호출이 자동으로 진행되는 연쇄를 만들지 않는다. 증거는 세션별 trace로 판정하며 이전 세션의 누적 read_order를 쓰지 않는다.

측정: 사례별 완료/중단, 요청한 내용·형식·편집 범위, 정상 자료 오거절, 반복 승인, 불필요한 사용자 개입, 다음 제안과 이유, 새 파일 효과, 실제 도구/모델 소비량. 의도된 차단·오탐·제품 오류·관찰기 오류·환경 제약을 구분한다. 자동 압축 복구·실제 adopter 품질·일반 완료율로 확대하지 않는다.

r2 변경은 이 계획의 문구·표시 계약·집중 검증 계획에 한정한다. 제품 코드/record/schema/실제 실행 권한을 변경하지 않았다. 예상2–4시간과 총300분 제안 상한을 유지하며 이미 소비한 R0/계획 보정 시간을 포함한다. 구현·행동 관측·R1은 아직 시작하지 않았다. 실제 설치·adopter 적용·Git 게시·공개는 계속 보류한다.

## 필수 보정

### 1. 실행과 현재 Work의 연결을 과장함
- **코드 확인:** `project_grant`의 allowlist(`src/hv2ref/official_schema.py:264`)에는 `target`, `scope.work_id`, installation digest가 있고, revision·intent 전용 필드는 없습니다.
- **미확인:** 발췌에 없는 `spec['target']`과 journal row의 내용은 확인하지 못했습니다. `work_scope_digest`를 현재 기록에서 재계산할 수 있는지도 알 수 없습니다.
- **문제:** “Work/intent/입력의 정확한 결속”과 “정확히 연결된 실행”은 현재 기록으로 충족하지 못할 수 있습니다. 반대로 결속 불명을 일괄 표시하면 대부분의 v2 실행에 같은 경고가 붙습니다.
- **보정:**
  - 연결 조건을 “검증된 grant의 `scope.work_id`가 조회 Work와 같고, `target`도 비교할 수 있으면 일치”로 낮춥니다. 준비 단계에서 `target`에 revision·intent가 없음을 확인합니다.
  - 표시 의미는 “이 Work 대상 실행 기록”까지만 둡니다. 현재 revision에 대한 실행, 승인, 제출본과의 선후는 주장하지 않습니다.
  - 시각, 파일명, digest로 revision을 추정하지 않습니다. `work_scope_digest` 일치도 이번 묶음의 표시 근거에서 제외합니다.
  - grant가 여러 개면 최신 하나를 고르지 않습니다. 미해결 실행의 건수와 ID를 시간과 무관한 고정 순서로 표시합니다.

권장 최소 문구:

```text
설치 안내 개선 (work-a)
확인 필요 · 이 작업 대상 실행의 문서 반영 여부가 불명확합니다.

실행 기록: abc123… (대상 작업 일치)
현재 작업: 검토 대기
연결 한계: 실행 당시 revision·intent가 기록에 없어 현재 revision과의 관계는 확인할 수 없습니다.
다음: 실행 기록과 현재 파일 대조
```

“연결 한계”는 unknown 또는 미종료 실행처럼 판단에 영향을 줄 때만 기본 화면에 표시합니다. 그 밖에는 상세 조회에만 둡니다.

### 2. CLI 사실과 agent 추론이 예시에서 섞임
- **문제:** 계획은 “다음” 줄의 fallback만 정의합니다. “README 설치 안내 보강”, “유지할 조건: … 게시 보류”, “확인 범위”, “후속 확인”도 구조화된 근거가 없으면 CLI가 만들 수 없습니다.
- **코드 확인:** 발췌한 `_work_overview`(`src/hv2ref/view.py:877`)는 상태와 continuation을 표시하며, 자유 서술을 해석하지 않습니다.
- **보정:** 근거 표에 “생산 주체” 열을 추가하고 다음 규칙을 둡니다.
  - **CLI:** 구조화 필드 원문과 고정 문구만 출력합니다. 근거가 없는 줄은 생략합니다.
  - **Agent:** 대화 응답에서만 추론할 수 있으며, 추론임을 드러내고 View 출력처럼 제시하지 않습니다.
  - **CLI fallback:** `다음: 현재 계획과 남은 작업 확인`, `참고(과거 기록, 실행 지시 아님): <next_action>`, `기록된 범위: <필드 원문>`을 사용합니다.
  - **라벨:** “유지할 조건”은 승인처럼 읽히므로 “기록된 범위”로 바꿉니다. CLI의 기본 검사 라벨은 “기록된 검사”로 두고, 미검증 범위는 “후속 확인” 대신 “확인되지 않음”으로 표시합니다.
- **완료 기준:** 세 예시의 합성 fixture를 “자유 서술 없음” 변형으로도 검사합니다. 추론 문장 없이 fallback만으로 다음 확인 행동이 이해되어야 합니다.

### 3. 종료 근거를 잘못 읽을 수 있음
코드에서 확인한 사항은 다음과 같습니다.
- `closure_refs`(`src/hv2ref/official_v2.py:54`)는 존재하는 종료·실패 row만 모으므로, 값이 있어도 전체 종료를 뜻하지 않습니다.
- `summary()['processes_closed']`(`src/hv2ref/official_v2.py:283`)는 runtime close 값 또는 `None`입니다. 전체 판정 메서드 `processes_closed()`(`src/hv2ref/official_v2.py:59`)와 이름만 같습니다.
- 메서드는 failure도 닫힘으로 처리하고, runtime intent와 worker가 모두 없으면 True입니다.

**보정:** “종료 기록” 문구는 `history.processes_closed()`가 True이고 실제 대상 프로세스 기록이 있을 때만 씁니다. summary 키와 `closure_refs` 존재 여부만으로는 판단하지 않습니다. 부분 종료, 실패 종료, 대상 없음을 검사에 추가합니다. `effect=applied`와 미종료가 함께 있는 조합도 포함합니다.

`stop_reason`은 발췌한 `summary()`에 보이지 않습니다. 준비 단계에서 확인되지 않으면 표에서 빼고 `status`만 사용합니다.

### 4. Work와 실행을 잇는 읽기 경로가 확인되지 않음
- **코드 확인:** `public_status`(`src/hv2ref/official_state.py:257`)에는 `work_id`, `scope`, `target`이 없습니다. `_work_overview`도 실행 이력을 입력으로 받지 않습니다.
- **미확인:** 기존 status/graph 관측만으로 Work의 grant 목록을 찾을 수 있는지는 발췌로 판단할 수 없습니다. 계획은 새 외부 읽기와 recovery 탐색을 금지하므로, 이것이 변경 효과 불명 화면의 실현 조건입니다.
- **보정:**
  - 준비 단계의 첫 확인 항목으로 둡니다. 경로가 없으면 범위를 넓히지 않고, 명시적 실행 조회나 기존 상세 경로에서만 이 화면을 제공합니다. 기본 View에는 “실행 기록은 이 화면에서 확인하지 않음”을 표시하고, 축소 사실을 보고합니다.
  - `scope`를 통째로 전달하지 않습니다. `scope`에는 문서 경로와 `recovery_store_id`가 있고, `summary()`에는 `recovery_locator`와 `rows`가 있습니다.
  - View에 필요한 값은 `work_id`와 종료 상태로 제한하는 allowlist를 둡니다. 경로, store, locator, 원문이 출력되지 않는 음성 검사를 추가합니다.

## 권장 보정

### 5. `unknown`을 중단으로 단정함
`effect()`(`src/hv2ref/official_v2.py:35`)는 result가 있어도 close returncode가 0이 아니면 `unknown`을 반환합니다. 따라서 “중단 시점의 문서 반영 여부”는 “문서 반영 여부”로 바꾸고, 중단 표현은 `status`가 뒷받침할 때만 씁니다. `recovery_availability='not_checked'`는 “복구 불가”로 번역하지 않습니다. v1 기록에는 effect 줄을 만들지 않습니다.

### 6. “다음” 한 줄의 우선순위가 없음
기존 코드는 “확인 필요”를 여러 줄 낼 수 있어, 한 줄로 줄이는 기준이 필요합니다. 다음 고정 순서를 권장합니다.
1. 기록 처리 미완료 또는 읽기 불가
2. 실행 effect unknown 또는 미종료
3. 현재 파일과 제출본 불일치
4. 수락·보완 결정
5. 일반 진행

기존 continuation 경고는 삭제하지 않습니다. 기본 View에서 생략하면 상세 조회로 연결합니다.

### 7. “재실행”이 소비된 grant의 재사용처럼 읽힘
`그다음: 복구·재실행 여부 결정`을 `그다음: 확인 결과에 따라 복구 또는 새 실행 승인이 필요한지 결정`으로 바꿉니다. 파일 대조 결과로 effect를 `applied`나 `none`으로 바꾸지 않는다는 점도 명시합니다.

### 8. 계획 기록이 서로 어긋남
R0 항목의 “이번에는 호출하지 않았다”는 R0 실행 승인 절과 충돌합니다. “r1 작성 시점에는 호출 0, 이후 승인으로 1회 소비, 잔여 제안 2회”로 고칩니다. 변경 기록의 “Claude 호출0”도 r1 시점 값임을 표시합니다. 계획 보정 처분과 소비량도 같은 문서에 남깁니다.

### 9. 집중 검사 추가
회귀 범위를 넓히지 않고 다음 fixture만 추가합니다.
- grant 이후 Work revision이 바뀐 경우
- 같은 Work에 grant가 두 개 있고 시각 순서를 뒤바꾼 경우
- 다른 Work의 grant가 섞인 경우
- 수락 대기 상태에 unknown 실행이 함께 있는 경우

기대 결과는 다음과 같습니다.
- 선택 결과가 시각에 좌우되지 않습니다.
- 다른 Work의 실행이 표시되지 않습니다.
- revision 연결이나 승인 표현이 없습니다.
- 원본 기록의 바이트가 바뀌지 않습니다.

### r2 문서 확인과 보존

계획과 Development index를 기존 고정 GFM parser로 렌더링해 코드 밖 literal emphasis가 없음을 확인했다. 로컬 링크 대상은 각각6개·70개를 확인했고 git diff --check도 통과했다. R0 응답 원문 일치와 외부 비교 식별 정보 미포함, 검토한 제품 입력5개 해시 불변을 확인했다. 이는 문서/정적 검사이며 제품 실행·행동 PASS가 아니다.

R0 준비부터 이 마감까지 계측 7.6249분(모델 대기111.981초 포함)을 새 구간으로 보존한다. 선행386.3551분과 더한 확인 가능한 계상은 393.9800분이며, 앞선 계획 작성 미계측분은 별도 불확실성으로 계속 남는다. 이를 완전한 전체 누적으로 표현하지 않는다. 준비 예약2분은 실측값에 다시 더하지 않는다. 전체2040분과 제안 묶음300분 상한, 호출1회 소비를 이월하며 사용자 승인 대기는 제외한다.

입력 packet·review identity·실행/종료 근거·응답은 후속 Driver의 실행 승인 확인과 R1 비교를 위해 기존 task 경로에 유지한다. 후속 결과 수락 때 재사용 필요를 재평가한다. r2 생성 스크립트는 적용·확인을 마쳐 소비자가 없으므로 삭제하고, 정본 계획·실행 자료·기존 실패 기록은 보존한다. 활성 source/task 경로는 변경하지 않았다.
