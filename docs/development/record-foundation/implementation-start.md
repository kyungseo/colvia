# 초기 구현과 조기 접근 진단 제안

상태: Owner 실행 승인됨, 2026-11-06. 첫 공개는 본문 보존·고지로 확정했고 아래 P0–P3 48시간·호스트 진단 6시간 및 명시한 리뷰/모델/합성 Git 범위를 승인했다. 리뷰는 Claude CLI로 진행한다. [R3b 처분](review-r3b-disposition.md), [보정 계약](implementation-contracts.md), [연결 경계](connection-edge-scope.md)를 합친 다음 실행안이다. 이 문서를 작성한 것은 구현·설정·모델 호출을 실행했다는 뜻이 아니다.

## 권장 결정 묶음

1. 첫 공개는 승인 파일의 전후 본문을 보존하고 개별 제거 미지원 조건을 안내한다. 개별 제거는 후속 후보로 남긴다. 첫 공개부터의 이력 보호·내보내기·복원·세대 전환은 유지한다.
2. 초기 P0–P3를 승인할 경우 아래 범위로 진행하고 일반 Work의 저장→검토→사람 수락→재개까지 확인한다. 실제 기존 설치와 사용 프로젝트에는 적용하지 않는다.
3. 이 Mac의 좁은 호스트 접근 진단을 별도 한도로 함께 승인하면 P0의 초기에 실행한다. 제품 설치·알림·키 생성·실제 Git 통합은 포함하지 않는다. 필요한 로그인/앱 동의만 사용자에게 요청하고 인증정보는 기록하지 않는다.
4. 실제 커밋·push·PR·병합·공개는 보류한다. 합성 fixture 저장소의 초기 commit/worktree 생성만 진단/시험 준비에 허용하는 것으로 분리 제안한다. 제품 저장소 커밋과는 다르다.

## A. 초기 제품 구현 — 예상 30–44 활동시간, 누적 중단 상한 48시간

| 순서 | 범위와 완료 기준 | 예상 활동시간 |
| --- | --- | ---: |
| P0 | R3b 보정과 기존 거부 규칙을 fixture로 연결. 기존 회귀에서 영향을 받는 기준만 고정하고 제품 코드 baseline 보존. 새 전체-suite 반복 없이 최소 검증 경로 준비 | 2–3h |
| P1 | typed envelope/고정 역할·정규형 tree·chunk/body·SQL root/CAS·세대/fence/pointer·조회와 import 검증 primitive. 손상/중단/깊은 이력/동일 본문 보존 집중 검사 | 12–17h |
| P2 | root/linked/app workspace identity·관측·D1/D7·opaque 경계·managed-entry 연결 interface. root 하위 실행, Git 전환 감지/보존, 실제 scope drift 안내. 새 자동 전환/기준점 갱신은 제외 | 8–12h |
| P3 | 일반 Work 계획/승인·편집 결과 제출·보완·한 번의 사람 수락·선택 조회/새 대화용 재개 상태. archive·후보/후속 기록을 공용 계층으로 연결. 짧은 기본 출력 | 8–12h |

범위: 기존 별도 foundation worktree의 Colvia 소스/시험/관련 문서. 기존 34개 제품 파일·회귀 근거와 수신기/빌더를 재사용하고 단계별로 옮긴다. 최초 공개 형식을 활성화하거나 설치된 프로젝트를 갱신하지 않는다. 새 구조만 병렬 구현해 버려지는 대체 제품을 만들지 않는다. P1의 export/restore 검증 primitive는 P7이 재사용하고, P7의 완성된 관리 명령·서명 bootstrap을 이 단계에 구현했다고 하지 않는다. P4–P9 기능을 제거한 것이 아니라 다음 승인 묶음으로 남긴 것이다.

시간은 새 기반 구현 실측이 아닌 판단치다. 이전 P0–P3 20–30h에 비해 세대 전환/fence와 참조 규칙·관측 분기를 실제 작업으로 배치했다. 중복되는 finding별 시간을 다시 더하지 않는다. 활동에는 구현, 집중 검사 실행/분석, 범위 내 문서·리뷰 반영이 포함된다. Owner·외부 reviewer 응답 대기는 제외하고, 겹친 작업은 한 번만 센다. 총 시험 wall time은 따로 남기며 동일 실행을 여러 단계에 중복 청구하지 않는다.

P1 종료와 P3 종료에 범위·진도·실측을 재산정한다. 48h 안에서 유지되는 보정은 반복 승인을 묻지 않는다. 근본 정책/권한 변경, 안전 조건 약화, 중단 상한 도달 시에는 멈춰 남은 것만 묶어 보고한다. 48h는 이번 초기 범위의 승인 제안이고, 전체 100h 누적 중단 기준에 포함된다. 전체 100h도 완료 보장이 아니며 자동 연장하지 않는다. 이미 소비한 구현시간이 있으면 착수 전에 이월한다. 이번 정적 설계/리뷰 시간을 새 구현 소비량으로 조용히 섞지 않는다.

검증: 순수 schema/tree/role/CAS/fence 집중 검사 → P2 topology/policy/opaque fixture → P3 scope·stale acceptance·재개 계약. 두 실제 모델의 완전한 사용자 여정은 이 소스 검사로 통과 처리하지 않는다. 필요한 전체 회귀는 누적 영향 검토 뒤 한 번 실행하고, 재사용 가능한 기존 결과를 반복하지 않는다. 재현 fixture의 의도적 실패는 검사지만, 실제 권한/호스트/미확정 효과 실패는 동일 입력으로 반복하지 않는다.

리뷰 제안: 새 전면 계획 리뷰는 추가하지 않는다. P1 핵심 저장/복구 결과와 P3 통합 결과에 기존 구독 Claude 정적 리뷰 최대 2회, 각각 180초 실행 한도. 합성 사례와 관련 제품 코드/검사 요약만 사용하고 계정정보·개인 경로·실사용 기록은 제외한다. 사용자가 직접 전달할 경우 그 회차를 CLI로 중복 호출하지 않는다. CLI를 사용할 때는 비밀을 출력하지 않는 인증/과금 경로 확인과 고정 패킷·허용 도구·timeout을 먼저 확정한다. 이 두 호출도 이번 묶음 승인에 포함해 달라는 제안이며 아직 실행하지 않는다.

## B. 조기 호스트 진단 — 예상 3–5 활동시간, 누적 중단 상한 6시간

초기 대상은 이 Mac의 Codex CLI/앱, Claude Code CLI/데스크톱 네 형태다. 설치되어 있는 도구와 기존 구독만 사용한다. 플랫폼/호스트 버전·현재 권한 모드와 실제 실행 파일을 기록한다. Windows ARM64/x64와 개인 Python 설정 없는 최종 배포본 검증은 이번 결과로 대신하지 않는다. 필요한 도구가 없거나 인증 경로가 예상과 다르면 설치하거나 결제 경로를 바꾸지 않고 해당 셀을 미실행으로 남긴다.

시험은 전용 합성 fixture 한 프로젝트의 primary/sibling linked root를 네 호스트에서 확인하고, 두 데스크톱에는 앱이 만든 nested worktree를 추가한다. 합성 파일·도구 요청만 사용한다. 새로운 모델 세션 최대 10개, 입력 메시지 총 16개, 모델 응답 대기 누적 30분. 실패 후 같은 셀을 자동 재실행하지 않으며 실패 이유를 분리하고 독립 셀만 기존 한도 안에서 진행한다. 호스트 재시작/설정 지속 확인도 같은 메시지 예산 안에서 수행한다. 실제 모델에 Work 본문을 작성시키거나 알림을 보내지 않는다.

진단 fixture/도구/결과는 기존 비공개 task artifact 루트의 `host-access-probe/` 하위에 둔다. fixture authority는 OS 사용자 데이터의 전용 `Colvia/authorities/probe-record-foundation-20261106/`만 대상으로 한다. 실행 전 소유·부재를 확인하며 충돌하면 재사용하지 않는다. 제품 정본이나 다른 프로젝트를 열어 시험하지 않는다. 사용 가능한 기존 runtime을 명시적으로 지정하고, 이것이 향후 새 관리 실행기 선택/개인 Python 없는 설치의 성공을 뜻하지 않는다고 기록한다.

허용 변경 제안: 위 fixture authority의 좁은 접근만, 필요한 호스트 설정에 추가하고 전후 diff를 보존한다. host가 그 범위를 지원하지 않으면 상위 사용자 데이터 전체 허용, sandbox 해제, 권한 우회를 하지 않는다. runtime/fixture 읽기·실행과 authority 쓰기를 분리한다. Git locator 생성은 합성 연결 준비에서만; 이후 sibling 첫 등록은 authority 쓰기만 요구하는지 확인한다. 기존 프로젝트·개인 Python·전역 Git 설정·OS 알림 설정은 변경하지 않는다.

| probe에서 확인 | 이후 재사용 조건 | 반드시 별도로 확인 |
| --- | --- | --- |
| 경로 기반 narrow allowlist와 DB/journal CRUD | 동일 host/mode/path 정책일 때 설계 근거 | 실제 관리 실행기의 command/executable별 승인, 설치 identity |
| 재시작 후 허용 유지, sibling/nested 읽기·authority 쓰기 | 같은 host 버전/설정 맥락을 기록 | 새 버전 앱의 설정 전달, 실제 배포본 위치/읽기·쓰기 |
| 기존 runtime으로 SQLite 접근 | 그 runtime/VFS/파일시스템에 한정 | 새 번들 Python/SQLite, quarantine/서명, 개인 설정 없는 설치 |

현재 host가 이미 넓은 쓰기를 허용하면 “형제 경로 차단 성공”을 주장하지 않는다. 격리된 기본 모드에서만 해당 부정 검사를 한다. 일반 폴더의 권한 결과를 sibling/app worktree에 추정하지 않는다. app worktree가 생성되지 않으면 수동으로 만든 폴더를 같은 셀의 통과로 바꾸지 않는다.

종료 원복: 추가한 설정 항목만 전후 비교로 제거하고, 다른 사용자의 동시 변경은 덮어쓰지 않는다. 호스트 재시작/재읽기로 설정 복원을 확인한다. 시험 프로세스와 connection을 정리한 뒤 필요한 결과/실패 증거를 artifact 경로에 보존하고 일회용 fixture authority를 제거한다. 불명 상태, 사용 중 process, 동시 설정 변경이면 해당 정리는 멈추고 정확히 남은 항목을 보고한다. 원복에 필요한 작업은 실패 시에도 남겨 둔 시간 안에서 우선한다. 설정 사본의 계정/개인 정보는 비공개에서만 최소 보존하고 제품 저장소/리뷰 패킷에 넣지 않는다.

6h에는 진단 준비, 조작, 모델 대기와 원복/결과 정리가 포함된다. Owner 로그인/직접 조작 대기는 별도다. 마지막 1h는 새 셀 시작에 쓰지 않고 원복/정리에 확보한다. 구현 48h와 중복 계산하지 않으며 기존 최종 qualification 제안 28h에서 앞당겨 쓰는 진단 소비량으로 기록한다. 동시 실행을 전제하지 않는다.

실패하면 해당 조합만 멈추고 좁은 허용/수동 확인 경로와 근거를 제시한다. 첫 공개 대상 축소, authority 위치 변경, 넓은 권한은 Owner 결정이다. 어느 host에서도 핵심 접근 경로가 성립하지 않으면 광범위 P2/P3 이식을 진행하지 않는다. 독립적인 P0/P1 작업은 안전한 범위에서 계속할 수 있다.

## 결정 후 진행

권장 승인 문안: “첫 공개는 본문 보존과 고지로 가고, 초기 P0–P3 48시간과 이 Mac 조기 호스트 진단 6시간을 승인한다. 제안한 두 정적 리뷰와 합성 fixture Git 준비만 포함한다. 실제 설치·제품 커밋·공개는 보류한다.”

Owner가 호스트 설정 변경을 지금 원하지 않으면 A만 진행할 수 있다. 그 경우 P2 실제 접근은 미검증으로 남기고 최종 경로를 확정했다고 하지 않는다. P0 시작 시 현재 소비량·checkpoint와 허용 범위를 기록한다. P3 종료 또는 상한 도달 시 결과·다음 P4–P9 범위/예측/한도를 한 번에 제시한다.
