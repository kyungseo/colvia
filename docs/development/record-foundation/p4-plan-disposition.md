## Fixed records and heads

All new records have exact fields, v1, fixed schema roles, project/instance supplied by the authority, and strict identifiers. Unknown/malformed required dependencies refuse. No arbitrary untyped JSON extension bypass.

- work.head adds required nullable context (decision edge): composition.binding or worker.binding. All new heads carry it; ordinary records use null. Plan replacement preserves role or requires the dedicated rebind path. Work transition validation checks context and membership in the common publication validator. Current schema is unactivated; old trial readers are not a compatibility target.
- composition.declaration: parent work ID, sorted unique case-insensitive child work IDs, integration_document, integration_checks; edges parent_plan, child_plans (decision), previous (provenance). One direct parent per child, no self/foreign/nested umbrellas. Child membership heads point at the exact declaration, with child identity and plan; role checks use this bidirectional relation. Ordinary child plan replacement after declaration is refused; dedicated parent rebind can explicitly replace declared child plans while preserving prior declaration.
- composition.binding: parent work/workspace, declaration (decision), captures (decision array), previous (provenance). A capture records child ID; exact plan, result, accept decision (decision edges), observed head (provenance). Capture may be incomplete for parent planning/start; submit/accept require exact full set and currently matching semantic refs. Children accepted under the existing bounded grant are marked in the capture. Historical validation checks saved chains without imposing current eligibility.
- Rebind is a new immutable parent plan/binding, replacing head with planned, clearing result/decision/approval in the new head and linking previous head as provenance. Only an exact human rebind receipt may initiate this from active/review/completed. It never accepts a result; new plan approval is required. No generic ordinary automatic baseline replacement. The linked previous head preserves old plan/capture/result/decision.
- worker.binding: application ID, source work/workspace, destination workspace, exact ordered scope; edges source_plan, source_approval, source_result, source_registration, destination_registration, destination_baseline, before_bodies, after_bodies (decision/integrity according to field); source observed head provenance. It is immutable and can be reviewed without writing destination files.
- worker.authorization: statement, actor, authority_kind human|delegated; binding (decision), grant nullable (decision). Delegated mode requires the exact isolated-worker grant. Human input is recorded faithfully but is not OS authentication. Outcome refers to this authorization; receipt binds project/instance/binding and current heads.
- worker.effect: application ID, phase pending|completed|cancelled, ordered transitions [{path,pre,post}], staging root identity and deterministic staged/evacuated names, created-directory identities where observed; binding/authorization (decision), observations/progress (integrity), previous (provenance). Completed requires exact whole intended destination result; cancelled requires every changed path pre and no durable completion. A progress marker alone never proves content effects. Unknown is derived observation, not completed state.
- worker.progress: exact application/path index, native identity/size/hash and phase prepared|evacuated|installed|verified; previous provenance. Mutable selection uses head CAS; actual filesystem observation, not progress ordinal, controls recovery. Recovery may see effect before progress publication.
- worker.grant: work, owner, delegate actor, action isolated-worker-accept, exact scope and source/destination IDs, statement; exact accepted plan and prior grant decision edges/provenance. State active|revoked. Creating/revoking grant is human; acceptance verifies current grant and plan, no parent role, no unknown effect and exact workspace binding. Delegate mode applies only through the worker service, not WorkService ordinary.accept.
- effect:pending singleton head selects the one pending worker.effect; completed/cancelled history remains reachable through application:<id>. Common writers check effect:pending inside CAS validation. Only exact recovery/cancel under the owned process lock and original authorization may mutate it. Existing read-set validation remains in force.

## File-effect protocol and ownership

Before reservation, verify writer port support, source/destination membership, destination full baseline, required body hashes, canonical/no-alias scope, exact grant/human receipt and absence of competing destination Work. Pre-stage post bodies in a private authority-owned per-application directory on the destination filesystem; sync, read back, record native identities. It is not inside the observed project. Staging files are reproducible from immutable bodies but evacuated user bytes are recovery-critical. Never delete them based only on a hash/expected path.

After the durable authorization/reservation and under a process-shared lock, recheck the original dependencies and filesystem. For each changed path: move existing occupant into the reserved empty evacuation name with no-replace; verify its identity/mode/bytes against exact pre. If unexpected, preserve evacuated bytes and attempt no-replace return to the original path only when vacant; otherwise keep both and report blocked. Before installing post, use an atomic no-replace operation so a concurrently created file is never overwritten. POSIX regular-file hard-link then unlink is allowed only with proven private staging identity and after cleanup the public file must have exactly one link; a crash with two links is classified through the recorded staged inode, never accepted as a normal hardlink. Prefer a platform-qualified exclusive rename where available. Never use os.replace on a user destination as a fallback. Deletion evacuates exact pre without replacement; preserve recovery bytes until terminal record and cleanup eligibility.

A crash between evacuation and installation yields a specific recorded missing+evacuated case, distinct from an ordinary pre-existing absence. Recovery validates the evacuation bytes and identities, and resumes only the original post intent. A mismatched file or unowned staging name blocks. Full outside-scope content/policy observation is checked before each effect and final commit. The destination root and traversed directory identities are verified, not only path text. External unsandboxed editors are not locked; tests inject their races and require byte preservation even when the outcome cannot complete.

Cancellation performs no user-file rollback. It is allowed only after verifying actual all-pre and no evacuated unresolved occupant; a no-replace return of a just-evacuated unexpected user file is narrowly part of failed write recovery, not undo of an accepted edit. Preserve the original failure and do not auto-retry.

## Corrected-plan review disposition before record implementation

The second fresh static review completed without input drift. Its source excerpts omitted several existing helpers; distinguish missing prose from a reproduced failure. No further policy choice is needed for the following bounded corrections.

- B2 accept durable order: sync staged regular files (including Darwin full device flush), exclusive move, sync both parent directories, flush the open regular file/device barrier where supported, then progress/terminal DB publication under the store's existing EXTRA/fullfsync settings. Any unsupported or failed durability operation remains uncertain; no power-loss qualification is inferred from unit tests. Crash oracles distinguish syscall success from durable publication. Never delete evacuation evidence on an ambiguous terminal commit.
- B3 accept: acquire the project effect process lock before reservation; after acquiring it re-read pending/application heads. First execution and resume share one observed-state executor.
