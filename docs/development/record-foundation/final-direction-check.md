# 구현 전 전체 방향 점검


현재 구현 진입 판단과 승인 제안은 [R3b 통합 초기 실행안](implementation-start.md)을 따른다. 아래 전체 견적은 과거 판단 범위이며 완료 보장이나 자동 실행 예산이 아니다. 본문 제거 정책은 Owner 미결이다.

2026-11-06 · Driver의 마지막 설계 점검. 기존 명세·R1/R2·시간 분해·규모·데스크톱 근거를 재사용했다. 새 성능 측정, 설치, 모델 호출, OS 설정 변경은 하지 않았다. [기존 Work](../FEAT-20261106-002-record-foundation.md)가 진행 상태를 소유한다.

## 결론

현재 방향으로 진행하는 것이 맞다. 문제를 정확히 기록하는 구조와 사용자가 적게 설명해도 되는 흐름이 이제 같은 설계에 연결돼 있다. 다만 “유연한 구조이므로 충분히 빠르고 오래 견딜 것”이라는 결론은 아직 낼 수 없다. 설계 방향은 적절하고, 성능·용량·실제 앱 접근은 구현 초기에 통과해야 할 조건이다.

공개 전 다시 정해야 할 핵심은 기록 위치·형식·수락 의미·본문 보존이었다. 이들은 이미 Owner 정책과 C1–C8에 포함돼 있다. 현재 점검에서 이를 다시 뒤집을 근거는 찾지 못했다. 아래 네 보완은 그 계약을 구현할 때 생길 우회나 비용 누락을 막는다. 새 기능 묶음이나 기반 재설계를 추가하지 않는다.

## 전체 평가

| 관점 | 판단 | 근거와 남은 확인 |
| --- | --- | --- |
| 제품 방향 | 적절 | 같은 프로젝트에서 작업 의도·정확한 결과·사용자 결정을 이어가는 목적에 집중한다. 더 많은 기록 자체가 효용은 아니므로 불필요한 재질문/설명을 줄이는 비용 기준이 필요하다. |
| 구조·책임 | 적절 | Domain/application은 Work 의미를, storage·OS·Git·host adapter는 실제 효과를 맡는다. 동일 개념의 중복 검사를 한 서비스로 모으되 경계 재검증은 유지한다. |
| 확장 | 필요한 경계는 있음 | OS/호스트가 달라도 같은 Work/수락 의미를 사용한다. capability와 workspace/attempt IDs는 미래 병렬화에 필요한 근거다. 미래 provider framework나 clone 자동 동기화까지 구현하지 않는다. |
| 일반 사용 | 방향은 개선됨 | 한 명령 준비, 전용 실행기, 맡긴 범위의 검토 준비까지 자동 진행, 사용자 수락 한 번, 짧은 결과/재개 안내. 실제 에이전트가 이를 지키는지는 별도 행동 검증이다. |
| 설치·갱신·해제 | 계약은 연결됨 | 다운로드/검증/Python 선택은 도구가, OS 허용·구독 로그인은 사용자가 맡는다. 갱신 실패와 데이터 호환, 해제 후 기록 보존도 이어진다. 한 명령이 무인 완료를 뜻하지 않는다. |
| 보편적 환경 | 목표는 충분, 실제 지원 미확정 | macOS ARM64와 Windows 11 ARM64/x64, 두 필수 에이전트의 CLI/앱. 개인 Python을 요구하지 않고 비 Git 작업에 Git을 요구하지 않도록 명시했다. 좁은 호스트 권한이 실제로 가능한지는 초기에 확인한다. |
| 누적 기록 | 기존 병목을 줄이는 설계 | Work마다 파일/전체 manifest 사본을 계속 만드는 대신 프로젝트별 SQLite와 공유 불변 객체를 쓴다. 한 사용자 전체를 DB 하나에 모으지 않는다. 저장된 본문 총량과 백업 비용은 계속 증가한다. |
| 성능 | 개선 근거는 있음, 수치는 미확정 | 기존 계측에서는 전체 graph·반복 topology가 큰 비중이었다. 선택 조회와 명령당 context 재사용이 그 원인을 겨냥한다. 파일 전체 관측 비용과 managed startup은 별도로 남는다. |
| 품질·복구 | 보호 조건은 강화됨 | exact-result 수락, CAS, chunk 게시, 완전한 backup/restore, Git 중단 판정과 첫 공개 이후 호환 계약이 있다. fault/성능/실제 플랫폼 시험 전에는 보장으로 광고하지 않는다. |
| 구현 복잡성 | 주의가 필요 | SQLite 외에 또 다른 저장 엔진·journal을 만들지 않고 trie를 순수 함수로 제한한다. updater는 표준 검증 구현을 재사용한다. 여러 의미의 “완료”를 하나로 합치지 않는다. |

## 구현 전에 명시한 네 가지

1. 조회와 전체 감사의 경계: 공용 root를 읽었다는 이유로 모든 Work와 과거 parent chain을 재귀 검증하면 현재 병목이 되살아난다. 필수 결정 의존과 이력 탐색을 형식에서 구분하고, 선택 조회 접근량을 실제로 검사한다.
2. 장기 저장 운영: 작은 파일 수가 줄어도 DB·본문·백업은 커진다. 용량/증가량을 볼 수 있고, 큰 export를 나눠 처리·취소하며, 공간 부족에서도 마지막 정상 기록과 백업을 보존해야 한다. archive는 화면 정리이며 공간 절약 약속이 아니다.
3. Git 없는 시작: 문서 작업용 일반 폴더에서 Git/개발 도구 설치를 첫 Work의 필수 조건으로 만들지 않는다. Git 작업에 필요한 조건은 해당 경로에서 따로 설명한다. Git 저장소를 도구가 없다는 이유로 비 Git으로 잘못 취급해서도 안 된다.
4. 호스트 접근을 일찍 확인: 전용 runtime과 프로젝트별 기록 폴더의 실제 읽기/쓰기는 전체 기능 구현 뒤 처음 확인할 항목이 아니다. P2의 작은 실행 경로가 준비되면 먼저 확인하고, 막히면 그때 연결 경로를 정한다. 현재 실제 설정/설치 보류는 그대로 유지한다.

이 보완은 [상세 계약](implementation-contracts.md), [검증표](validation.md), [순서·비용](implementation-plan.md)에 반영했다. 기존 구현 예상 50–75활동시간/제안 중단 상한 100시간을 늘리지 않고 해당 단계 안에 배치했다. 측정 후 근거가 달라지면 숨기지 않고 재산정한다.

## 오래 쓰면 얼마나 커질 수 있나

아래는 제품 실측이나 상한이 아니라, 매번 새로 보존하는 고유 본문량만 곱한 예다. 이전/이후 중 이미 보존된 bytes는 중복 계상하지 않았고, dedup 이득·압축률은 가정하지 않았다.

| 제출 횟수 × 회당 새 고유 본문 | 본문만의 단순 합계 |
| --- | ---: |
| 1,000 × 100 KiB | 약 98 MiB |
| 1,000 × 10 MiB | 약 9.8 GiB |
| 10,000 × 20 KiB | 약 195 MiB |

메타데이터·DB index/page·staging·runtime·백업 공간은 이보다 추가된다. ZIP 기반 문서나 이미지/영상처럼 변경 때 많은 bytes가 달라지는 자료는 chunk 중복 제거가 거의 도움이 안 될 수 있다. 보존하는 내용을 모두 지키면서 무한히 작은 공간을 쓰게 할 수는 없다. 그래서 지원 규모를 파일 수 하나로 정하지 않고 현재 파일/bytes, Work/제출 수, 변경 본문량, 조회/백업/복구 시간을 함께 측정한다.

목표는 오래된 기록 때문에 평소 조회가 계속 느려지거나, 이미 수락한 내용을 잃는 일이 없도록 하는 것이다. 모든 크기의 저장소에서 매 명령이 즉시 끝난다는 목표가 아니다. 큰 관측에는 진행/취소와 정확한 한도 안내가 필요하다.

## 다음 순서

이번 보완까지 고정한 집중 리뷰 입력을 준비한다. R2 지적을 다시 처음부터 조사하는 대신 닫힌 상세 계약과 위 네 가지가 실제로 모순 없이 연결되는지 확인한다. 리뷰 보정 뒤 P0 회귀 기준 고정, P1 store, P2 가장 얇은 host/권한 경로, P3 일반 Work로 진행한다. 실제 설정·설치·키 생성·커밋·공개는 계속 보류하며 외부 모델을 이번 점검에서 호출하지 않는다.

현재 판정은 “이 방향으로 구현할 가치와 근거가 충분함”이다. “성능·플랫폼 품질까지 이미 검증됨”이 아니다. 추정으로 넘어갈 수 없는 부분은 P1/P2의 조기 중단 조건으로 남긴다.
