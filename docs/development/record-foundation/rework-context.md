# Ordinary rework after another Work adds files

Status: Owner-authorized narrow contract amendment; source implementation, focused verification and three static review rounds completed, with final narrow review corrections checked by the Driver. Owner result acceptance remains separate. This is not installed-runtime qualification. It extends C5 only for the case below. Original trial drafts and failure evidence remain private and unchanged.

## User outcome and boundary

A person requests a modification to an already submitted result. Another Work has meanwhile added files and submitted them in the same workspace. The agent must be able to revise the first Work inside its approved scope, perform the planned checks and submit again without an unrelated, attributable addition blocking it. A new conversation must recover the recorded modification request, approved files/checks, current scoped differences and any current blocking cause without requesting the same approval again.

This is not arbitrary baseline refresh, automatic merge, parallel execution, or recovery of general pull/rebase/branch-switch changes. Initial submissions do not get this exception. Unknown additions, existing outside modifications/deletions, scope overlaps, instruction/hidden paths, policy/structural changes and unproved identity remain refusals. A file's attribution describes agreement with retained records/content, not proof of its author.

## Immutable proof and live admission

Keep the original plan, approval, baseline membership, previous submissions and body bytes unchanged. Add `work.submission` version 2 only when attributed paths are needed. Its `attribution` decision edge points to an existing canonical map from path to an immutable version-1 peer submission. No new database table or peer-head dependency is introduced.

For every new path, prove all of the following:

- It was absent from both the original Work baseline and the peer baseline; it is a regular addition inside the peer's approved scope and recorded changed set.
- The peer is a different approved Work with a current submitted or completed v1 result in the same authority/workspace/registration. Its entire approved scope still agrees with the current single observation.
- The peer scope does not overlap the current Work scope, including case aliases or ancestor paths. The new path cannot overlap protected baseline membership or instructions.
- Original/peer policies, identities, structural membership and opaque context agree. The proof's entry exactly matches the current observed bytes/mode.
- All planned check reports are present and passed. This is a reporting requirement, not independent proof that the agent executed them; the agent must actually rerun the relevant checks.

Use the original membership plus these proved entries for the outside-scope comparison. The current result's changed paths and retained before/after bodies remain limited to its own approved scope. Pin peer heads and the discovery root at publication and re-observe the full protected tree before publication. The existing short publication CAS checks that root again, including heads that were skipped or created after discovery; an intervening unrelated authority change can therefore refuse this narrow admission. This does not introduce parallel execution or a new storage primitive. The prepared-submit delivery route must enforce the same peer-head check before its preparation becomes authoritative. Later delivery publication validates that sealed proof and requires the entire current protected observation to equal the prepared observation; a peer decision changing without a file change does not rewrite this retained proof. The discovery CAS closes ambiguity through authoritative preparation; a newly submitted second claimant after preparation does not rewrite the sealed proof. No notification is involved in source tests.

Later revisions carry a flat superset of previous adopted paths with identical refs. Modification or deletion of an already adopted entry remains protected. Downgrading an attributed revision to v1 cannot remove that protection: the v1 schema locally rejects a v2 previous ref, including an intermediate historical record in that submission chain during import. This does not authenticate arbitrary fabricated backup/head history. A later revision of the same peer cannot silently replace a carried ref. If another addition would require two different revisions of one peer, both current diagnosis and publication refuse and preserve the drafts. Peer results that themselves use v2 are not eligible as new proofs in this version, avoiding recursive attribution chains. Existing previous-result provenance is retained; there is no new chain through peer heads.

Bounds: 16 peer submissions, 1,000 attributed paths, discovery of at most 1,000 current Work heads, at most 32 candidate peers passing cheap filters before full-tree reads, and at most 30 displayed diagnostic entries with total/omitted counts. Attribution map reading stops at its entry limit, rather than materializing a general map first. Case-folded exact-path and ancestor indexes avoid scope cross-products; these checks are proportional to path depth. These are admission limits, not a large-project performance qualification. Exceeding a bound refuses without changing the Work head. Discovery does not walk Work history. One shared semantic function checks the live observation and sealed proof, including the whole peer scope, registration, policy and structural context even when a revision only carries prior attribution. Shared schema content validation rechecks the proof during publication, graph audit and import. Historical v2 proof validation is not memoized across revisions; full-tree work remains bounded but needs future large-history measurement. Registered structural containers/nested roots are worktree boundaries, not ordinary directories. Existing and new ordinary subdirectories use the same regular-file rule. Context refusals name changed boundaries; mixed original/attributed file refusals give each file its own matching condition. Instruction exclusion covers hidden components and known entry names (including CLAUDE.local.md); it is not a semantic detector for arbitrary instruction filenames.

## Resume and refusal contract

`ordinary view` exposes stored plan checks in all states. Active rework also includes the recorded request, approved scope/checks, last submitted revision, current scoped path differences and a bounded current submission diagnosis. `scope-checked` means only that this scope comparison passed; planned checks and actual submission still remain. An active Work's last submission is retained history, not a currently pending review. The read does not establish whether checks ran in another conversation. A read never publishes a new decision or records a past failure as if it were current. If observation fails, return unavailable instead of inferring permission or a successful comparison.

A confirmed `outside-scope-change` remains exit 2 with stable error/message fields. Optional bounded details list causal paths, addition/modification/deletion, reason and the next action. The human message names those files and tells the person to identify their origin/scope while preserving current drafts and other Work files. For a changed carried file it also names the peer Work and explains that exact agreement with the retained submission is required; it never automatically restores that file. A changed policy names the policy source. Only causally overlapping paths appear in an overlap refusal. The view distinguishes whether all planned checks must pass for an attributed result; failed or unavailable checks must not be reported as passed. It never instructs baseline/record manipulation, automatic deletion or a retry of an unknown effect. Unresolvable external changes remain outside this amendment. The agent asks only about a real new scope/target/effect decision; result acceptance remains separate.

## Compatibility and consumers

Existing v1 submissions remain readable. Once v2 records are published, a reader without that schema capability must refuse the project; returning to an older runtime is not a way to remove required history. Export/import carries and validates the v2 proof along with bodies. Acceptance still records a human decision about this Work's result only. Git selection continues to select only this result's changed paths and body map. Composition captures use the same result validator.

Worker application of attributed v2 results to another workspace is explicitly unavailable in this candidate, before filesystem effects or application records. Existing v1 worker behavior is unchanged. A future worker extension needs its own target-protection contract; neither a private copy script nor ignoring attribution is an alternative.
