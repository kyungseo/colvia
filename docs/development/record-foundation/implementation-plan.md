# 구현 순서와 기능별 비용


현재 구현 진입 판단과 승인 제안은 [R3b 통합 초기 실행안](implementation-start.md)을 따른다. 아래 전체 견적은 과거 판단 범위이며 완료 보장이나 자동 실행 예산이 아니다. 본문 정책은 첫 공개부터 보존하고 그 한계를 고지하는 것으로 Owner가 확정했다. 아래 과거 견적·단계 제안은 당시 판단으로 남기며, 현재 실행 권한과 완료 상태는 owning Work 및 단계별 checkpoint를 따른다.

상태: 2026-11-06 Driver 실행안. [상세 계약 C1–C8](implementation-contracts.md), [거부 규칙 RF-01–36](refusal-map.md), [회귀 기준](validation.md)을 구현 단위로 나눴다. 설계 정리의 완료이며 제품 구현·설치 검증의 완료가 아니다. 현재 묶음은 문서와 정적 목록만 변경한다.

## 권장안

첫 공개부터 지킬 기록·본문·수락·갱신 계약을 먼저 고정하고, 저장 계층부터 기존 기능을 하나씩 연결한다. 새 형식과 옛 형식의 이중 쓰기나 자동 이관은 만들지 않는다. 과거 시험 제약은 정리하지만 일반 Work, 후보·후속, worker·umbrella, 선택형 공식 실행, 맡기기·알림, 연결·갱신·복구·해제 능력은 유지한다. 기능을 뺄 때는 일정이 아니라 정확성·제품 범위의 이유로 Owner가 결정한다.

일반 사용 흐름은 다음과 같다.

```text
한 명령 설치/갱신 → 전용 실행기 → 프로젝트 연결
                              ↓
                 공용 기록 + 작업 폴더별 결과
                              ↓
               맡긴 범위의 수정·검사·검토 준비
                              ↓
                    사용자가 결과 수락
                              ↓
          새 대화에서 재개 / 필요할 때 별도 Git 통합
```

## 예상 시간과 상한

초기 재사용 가정의 견적은 활동 시간 50–75시간이었다. 추가 검토 후 현재 작업 예측은 활동 시간 75–120시간으로 보정한다. P4/P5/P7의 보수적 범위를 반영한 판단치이며 실측이 아니다. 제안하는 누적 중단 상한은 100시간이다. 기존 32–52시간은 기능 이식 비용이 빠져 전체 견적으로 사용하지 않는다. 100시간은 예상 시간이나 이번에 새로 승인된 실행 예산이 아니다. 기존 승인 한도를 넘겨 계속하는 근거로 삼지 않고, 구현 착수 전에 적용할 누적 한도를 Owner와 확정한다.

이 수치는 새 코드를 작성해 본 실측이 아닌 판단 견적이다. 근거는 현재 34개 제품 파일 17,912줄의 정적 조사, 기존 회귀·설치·실습 근거, 이미 확인한 반복 관측/검증 비용과 새로 필요한 계약이다. 줄 수에 시간 상수를 곱하지 않았다. 가장 큰 불확실성은 호스트 권한 전달, SQLite 중단 복구, signed bootstrap의 플랫폼 이식, Git ref/index 복구다. 기존 수신기·빌더·fixtures를 재사용하고, 새 동시 실행 스케줄러·과거 형식 이관·새 플랫폼은 만들지 않는 조건이다.

활동 시간에는 설계의 범위 내 보정, 구현, 집중 시험의 실행/분석, 문서, Driver의 리뷰 반영을 포함한다. 외부 Reviewer나 Owner 응답을 기다린 시간과 인증 대기, 다운로드·VM 설치 대기는 포함하지 않는다. 겹쳐 수행한 일은 한 번만 센다. 따라서 이 시간 범위를 곧바로 달력상의 공개일로 바꾸지 않는다. 실제 설치본·앱·OS·공개 경로 검증은 아래 별도 묶음이며 이 숫자 안에 완료했다고 보고하지 않는다.

P0→P1→P2→P3 순서로 실제 쓸 수 있는 세로 경로를 먼저 만든다. P4–P8은 공통 store/identity를 재사용하며 단독 제품을 각각 다시 만들지 않는다. P7의 runtime/backup interface는 P1/P2에서 계약대로 고정하고, 전체 설치 흐름은 기능 통합 뒤 연결한다. P8은 일반 수락 완료와 독립적으로 시험한다. 병렬 에이전트나 실제 병렬 작업 실행은 이 계획에 포함하지 않는다.

표의 기존 단계 한도는 합쳐 100시간이며 대기 제외 기준은 전체와 같다. 보정된 P4/P5/P7 예상은 옛 배분을 넘으므로 해당 한도 안에 완료한다고 주장하지 않는다. 옛 배분은 재점검 기준이며 실행 일정으로 그대로 활성화하지 않는다. P1/P2/P3 결과 뒤 남은 범위/한도를 재배분해 Owner에게 제시한다. 단계 상한에 닿거나 예상이 실질적으로 달라지면 남은 일·소비량·변경 근거를 정리하고 계속할 범위를 확인한다. P1/P2 결과 뒤 첫 재산정, P3 종료 뒤 기능별 잔여 비용 재산정을 한다. 남는 시간을 다른 단계의 무제한 재시도에 쓰지 않는다. 실패 횟수와 이전 중단 기록은 유지한다.

## 중복을 줄이는 방법

- 동일한 scope/receipt/body 검증은 command별로 새로 구현하지 않고 application service 하나에서 소유한다. OS와 호스트 차이는 port로 처리한다.
- 플랫폼이 바뀌어도 순수 schema/trie/store 의미는 같은 fixture를 쓴다. native 파일 잠금·경로·권한·알림은 공통 시험 통과로 대신하지 않는다.
- P1에서 한 번 만든 중단/경합 harness를 P3/P7/P8이 재사용한다. 각 단계에는 새 외부 효과와 복구 postcondition만 추가한다.
- 기존 수신기 표시/UI, payload 구성, 언어별 가이드 구조와 무관한 파일형식 근거는 변경 영향이 없을 때 재사용한다. 새 locator, 새 본문 저장, 새 updater 신뢰 경로는 재검증한다. 새 검증 라이브러리는 버전/해시·라이선스·필수 고지를 확인하고 배포 목록에 포함한다.
- 반복적으로 전체 옛 테스트를 실행하지 않는다. 이식 중에는 해당 RF-T와 계약의 집중 검사를 쓰고, P9에서 누적 변경이 storage/lifecycle/execution 전체에 걸치므로 관련 전체 의미 회귀를 한 번 모아 확인한다. 옛 profile/JSON bytes를 통과시키기 위한 호환층은 만들지 않는다.
- 기존 시간 분해·규모 측정과 실패 fixture를 비교 기준으로 보존한다. 작업 하나의 전체 모델 시간만으로 개선을 판단하지 않는다.

## 비용과 규모의 완료 기준

새 구조에서 같은 합성 데이터로 실행기 기동, 관측, 저장/결정, 선택 조회, 목록 조회, 본문 작성, 모델 대기, 사용자 결정 횟수를 분리한다. 기록 처리 감소가 모델 혼잡도에 가려지거나 반대로 모델이 빨랐던 것을 제품 개선으로 세지 않는다.

- 정상 승인 후 수정/검사/검토 준비까지 추가 제출 요청이 없어야 하고, 수락은 정확한 결과를 한 번 확인한 결정으로 끝나야 한다. 범위 확대·판본 변경·모호한 대상에는 필요한 질문이 남는다.
- 100/1,000/3,000파일과 기존 30Work 사례, 완료된 69Work 사례까지 비교한다. 중단된 100/300Work를 과거 통과 기준으로 쓰지 않는다. 새 100/300Work 증량은 앞 단계 비용/안전 조건이 충족될 때 해당 단계의 시험 예산 안에서 수행한다.
- 변경하지 않은 tree/body가 Work마다 전체 복제되지 않는지 고유 객체 수와 논리/실제 저장량으로 확인한다. Git pack과 raw DB/파일 크기는 별도로 보고한다.
- 선택 Work 조회가 전체 과거 Work 수에 비례해 모든 그래프를 다시 읽지 않는지 접근량으로 확인한다. archive 뒤 본문·결정·연결을 잃으면 공간이 줄어도 실패다.
- C3의 큰 본문에서 reader delay와 busy 종료를 기록한다. 공개 최대치나 SLA는 측정 전 숫자로 선언하지 않는다. 성능이 기대보다 나쁘면 명세/구현을 보정하며 데이터 보호를 빼서 수치를 맞추지 않는다.

## 리뷰와 다음 권한 경계

R1/R2의 근거와 처분을 재사용한다. 후속 집중 구조 리뷰는 C1–C8·RF 표·비용 변경분을 입력으로 삼고, 저장/관측 경계가 닫힌 시점과 통합 결과 시점에 필요한 결과 리뷰를 묶는다. 현재 묶음에서는 새 Claude 호출을 하지 않는다. 리뷰 원문·실패 증거는 보존하고 Reviewer 통과를 Owner 수락으로 바꾸지 않는다.

실제 검증은 제품 후보가 만들어진 뒤 한 묶음으로 제시한다. 예상 12–20시간 활동, 제안 상한 28시간의 플랫폼 검증 예산을 잠정 분리한다. 준비된 세 OS/아키텍처 환경과 로그인된 네 호스트 형태를 가정한 판단치이며, x64 환경 미확보·인증·OS 설치·외부 확인자 대기는 별도다. 그 조건이 없으면 달력 완료일을 약속할 수 없다. 이 예산과 실제 실행은 아직 승인되지 않았다.

검증 대상은 macOS ARM64, Windows 11 ARM64/x64 × Codex CLI/앱, Claude Code CLI/데스크톱의 12개 조합이다. 기본 폴더·linked worktree·앱 내부 worktree, 개인 Python 설정 없는 환경, 읽기/쓰기 권한, 실제 managed entry, 첫 Work→결과→알림 클릭→재개를 매핑한다. 같은 native 알림 수신기 등 동등한 기반 근거는 재사용하되 호스트별 실행기·지침·권한 연결의 관측을 생략하지 않는다. 원래 기능이 없는 조합은 이유를 기록하고 지원 가능성/실제 확인을 구분하며 임의로 지원 완료로 표시하지 않는다.

첫 공개의 설치/업데이트/실패복구는 실제 배포 주소·서명 root·최종 파일로 확인해야 한다. 현재의 소스·fixture 검증이 이를 대신하지 않는다. 커밋, 설치, 설정 변경, 키 생성, 모델 실습, 공개는 각각 기존 권한을 확인하고 진행하며 이 문서가 새 실행 권한을 만들지 않는다.

## 공개 이후로 남기는 것

Linux, 새 에이전트/로컬 모델 실행 도구, 실제 병렬 실행 스케줄러는 기존 후속 후보로 유지한다. 공개 뒤 덧붙일 수 있도록 capability·OS/host ports·workspace/attempt ID를 갖추되 미래 framework를 구현하지 않는다. 기록 형식·위치·수락 의미·본문 보존·백업·첫 공개 이후 갱신 보호는 이번 공개 전 필수다.

현재 실행 묶음의 예상은 45–75분 활동, 자체 중단 한도 90분이며 구현 예상과 다르다. 문서/정적 목록 검증만 수행하고 실제 설정·설치·키 생성·커밋·공개는 계속 보류한다.


## 마지막 방향 점검에 따른 순서 보완

[전체 방향 점검](final-direction-check.md)에서 기본 구조를 유지하되 네 항목을 명시했다: 조회의 필수 의존과 과거 이력 탐색 분리, 본문 누적·export/복구 용량의 운영 가능성, 비 Git 경로의 Git 비의존성, 실제 호스트의 좁은 접근 확인 시점이다.

추가 제품 묶음을 만들지 않고 P1의 query/store, P2의 non-Git/host 진단, P7의 storage summary/export, P9의 규모 시험에 배치한다. 50–75시간 예상과 제안 상한 100시간은 유지하되 첫 P1/P2 재산정에서 실측으로 확인한다. P2의 가장 얇은 실행기/authority 읽기·쓰기 경로가 준비되면, 네 호스트의 실제 접근 확인을 전체 기능 이식보다 먼저 제시한다. 이는 기존 최종 검증 예산 중 해당 셀을 앞으로 옮기는 것이며 새 설치·권한 변경 승인이 아니다. 기본 접근이 막히면 나머지 이식을 계속 쌓기 전에 해결 경로를 결정한다.

P1 시험에서 선택 조회의 읽은 객체 수와 역사 증가의 관계를, P7에서 무중복 큰 binary 본문/중단된 export/복구 공간을 함께 본다. 전체 history를 읽는 구현이나 archive가 공간을 줄인다는 잘못된 주장은 다음 단계로 넘기지 않는다. 새 자동 정리나 선택적 기록 폐기는 구현하지 않는다.


## Additional advice before R3

[보충 의견 처분](direction-advice-disposition.md)을 반영했다. 기본 기능 구현 예상은 이제 75–120활동시간, 실제 qualification을 합치면 87–140활동시간의 판단 범위다. 제안 중단 상한 100시간은 자동 확대하지 않으며 완료 보장도 아니다. 앞부분의 50–75 및 “견적 유지” 기록은 당시 판단이며 이 절이 현재 예측이다. 본문 제거 정책/명령의 비용은 Owner 결정과 상세 검토 후 별도 명시해야 하므로 아직 포함했다고 하지 않는다.

P7에는 최초 신뢰 bundle 준비와 기존 trusted updater의 분리, freshness 자동 갱신·만료 감시·중단 복구 절차/fixtures를 명시적으로 포함한다. 만료 주기를 무조건 늘려 비용을 줄이지 않는다. P0–P3 조기 진행은 유지하고, P4 이후는 이식 결과를 보고 정확히 재산정한다.
