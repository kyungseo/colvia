# 최소 실행 정책·Claude 조회 검증 결과

상태: 승인한 실행·리뷰·오프라인 보정을 마쳤다. 묶음 전체는 통과하지 않았다. 실제 설치·공개에 사용할 수 있는 후보로 보지 않는다.

## 확인한 것과 남은 것

| 경로 | 실행 결과 | 판단 |
| --- | --- | --- |
| 최소 문서 정책 | 진단 부록과 외부 gettext 읽기 예외를 제거했다. 새 작업자는 준비 신호 전에 종료(-6), stderr 0바이트, 관측된 프로세스 종료 확인 | 시작 실패의 원인은 미확정이다. 조건부 문서 5단계는 실행하지 않았다. 읽기 권한을 다시 늘리거나 우회하지 않았다 |
| Claude 조회·최종 답변 | 약15초, 정확한 조회1회와 응답1회, 정상 exit0·EOF·고정 CLI 버전/실행 파일 일치. 프로젝트·정본 전후 동일 | 실행·조회 및 최종 답변 수신은 통과했다 |
| Claude 상태 설명 | 실제 Work는 수락 완료이며 현재 파일도 같다. 답변은 '수락은 하지 않았고, 수락 여부는 직접 정하시면 됩니다'라고 설명했다 | 사전에 정한 의미 품질 조건에 어긋난다. 통신 성공을 전체 성공으로 표시하지 않는다 |

현재 source template는 실행 실패가 남은 진단 후보다. 배포·설치본 qualification은 보류하며, 기존 넓은 정책으로 되돌려 같은 시험을 통과시키지 않았다. 이전 성공/실패 증거와 이번 실패를 모두 보존한다. 기존 정책 아래의 성공을 이번 정책의 성공으로 재사용하지 않는다.

## 소스 변경과 검사

제품 수정은 `runtime/official/worker.sb.in`, `tests/test_foundation_worker_plan.py` 두 파일이다. renderer와 제품 process port는 변경하지 않았다. 쓰기 시 부모 디렉터리 data 접근이 허용된다는 기존 동작을 주석에 정확히 적었다.

- 정책/입력 경계11개: 통과(6.563초). 빈 문서 목록은 기존 계약의1..8개 제한으로 거부된다. renderer 변경은 불필요했다.
- 시험 연결부20개: 통과. 추가 gate 검사는25회 실행했으나 상속에 의한11개 중복이 있어 고유 조건은14개다. 숫자를 독립 검증 수로 합산하지 않는다.
- 기존 제품 버전 경계33개, 이전 Codex 작성·제출·수락, 공급 목록·전체 Mach-O10개 대조는 재사용했다. 제거한 gettext 경로는 원 load/weak/reexport/rpath 기록에 없었다. 이 사실은 모든 동적 기능 실행을 입증하지 않는다.
- CLI 버전2.1.318과 실행 파일을 고정했다. init 버전, EOF 수신/잔여 buffer, message/result의 세션 일치 조건을 강화했다. CLI 제한과 wrapper가 실행을 제한하며 decoder는 관측·중단 역할이다. 이를 독립 OS sandbox로 표현하지 않는다.

## 후속 판단

1. 최소 정책 준비 실패: 어느 시스템 읽기 조건이 필요한지 실패 근거로 좁혀야 한다. 현재 종료 코드만으로 필요한 규칙을 선택하지 않는다. 새 실행과 권한 규칙 변경은 다음 명시적 범위에서 판단한다.
2. 수락 상태 설명: view의 `completed` 표기와 agent 안내, 이번 호출에서 수락하지 말라는 지시가 기존 수락 상태와 혼동되는지 대조한다. 현재 출력만으로 단일 원인을 확정하지 않는다. 이미 수락한 결과를 다시 수락하도록 요구하지 않는 것이 완료 기준이다. 이번에 product view/adapter를 임의 변경하거나 모델을 재호출하지 않았다.
3. 실제 설치본·앱·Windows, 알림 클릭, 배포 경로 검증은 별도다. 미완료 외부 효과가 있는 복원본은 계속 조회 전용이다.

원시 실행 결과의 `ok=true`는 Claude 실행/명령 감사에 대한 값으로 보존한다. 이 묶음의 판정은 별도 의미 검토를 포함한 부분 확인·미통과다. raw evidence를 수정해 실패를 숨기지 않는다.

## 답변 오류에 대한 추가 정적 대조

제품 adapter에는 이미 completed 상태는 새 수락 질문이 필요 없다는 규칙이 있다(`adapters/foundation-work/SKILL.md`, Resume and inspect). 이번 제한된 조회 fixture는 그 adapter 전체를 읽지 않게 했고, '정확한 조회만 수행'하는 짧은 CLAUDE.md를 사용했다. 따라서 이번 사례는 축약 fixture에서의 상태 설명 오류이며, 실제 설치 adapter를 따른 세션에서도 동일하다고 일반화하지 않는다. `WorkService._head`는 completed의 decision action이 accept임을 검증하고, `view`는 state와 재개용 receipt를 내보낸다. 다음은 제품 계약을 새로 만들기 전에 fixture가 이 기존 의미를 전달했는지 맞추는 것이 우선이다. 이 대조는 정적 확인이며 새 모델 실행은 없다.

## 최종 리뷰·보정 처분

계획 리뷰338.661초·결과 리뷰105.964초를 완료했으며 두 입력 모두 drift가 없었다. 결과 리뷰 후 변경된 정책 검사6개는4.565초에 통과했다. 이전11개 중 입력 검사5개는 재사용하고, 중복 수치를 합산하지 않는다. 보정 뒤 실제 실행·추가 모델 호출은 없다.

- D1 defend: 실제 renderer는 설명을 포함한 marker 전체 줄을 치환한다. 저장 profile에 남은 설명이나 marker는 없다. 문구를 옮겨 renderer를 깨뜨리지 않고, read/write의 실행 줄·쓰기 규칙이 주석에 가려지지 않는 검사를 강화했다.
- D2 accept: rendered read는 /dev/null 이외 쓰기, network/mach/fork/ipc 권한이 없고 exec가 하나임을 검사한다.
- D3 accept: 문서/read_ids의0·9개 조건을 각각 검사하며 플랫폼 독립 schema 시험으로 옮겼다.
- D4 accept: 시험 이름을 release 대신 candidate로 고쳤다. 성공하지 않은 native 경로를 공개 지원으로 표시하지 않는다.
- D5 revise: 원인은 미확정이다. parent exit-6·signal0과 종료 직전 parent 부재는 저장돼 있다. 종료 helper는 group_absent 조건을 통과했다고 기록했지만 원 ps 전체 출력은 보존하지 않았다. 독립적인 전 프로세스 부재 감사로 확대하지 않는다. marker 형식이 바뀌었다는 리뷰 추론은 실제 diff와 다르다.
- D6 defend: 실제 조회 응답은 revision1·archivedfalse도 포함하므로 그 설명에는 근거가 있다. 수락 전이라는 설명만 상태와 어긋난다.

실제 Claude init의 tools는 Bash 하나, MCP는 없었지만 permissionMode는 default였다. 요청 argv의 manual을 실효 manual 권한 증거로 표시하지 않는다. 이번 결과는 협조적 제한 시험의 명령·응답 감사이며 호스트 전체 권한 또는 OS sandbox의 검증이 아니다. resource 변경 시험은 별도 fixture 복사본만 수정했다.

계획·실행·결과 리뷰·범위 내 보정은 마쳤다. 묶음 판정은 부분 확인·미통과이며 Owner 수락 전이다. 소스의 축소 정책은 실패가 남은 진단 후보로 보존한다. 설치·권한 변경·키 생성·알림·Git 게시·공개는 보류한다.
