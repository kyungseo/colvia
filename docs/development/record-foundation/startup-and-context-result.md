# 시작 조건·제품 지침 조회 결과

상태: 실행·집중 검사·계획/결과 독립 리뷰와 범위 내 보정을 마쳤다. Owner 결과 수락과 실제 설치본 검증은 별도다. [실행안](startup-and-context-followup.md)의 승인 범위 안에서 수행했다.

## 결과

| 확인 | 관측 | 판단 |
| --- | --- | --- |
| A: OS cache 디렉터리·조상 metadata 읽기 | 준비 전 SIGABRT, 약1.25초. 실행 신원과 종료 확인 | 다음 다른 조건으로 진행 가능한 승인된 반례 |
| B: A + 확인한 cache 파일·디렉터리 data 읽기 | 준비 전 SIGABRT, 약1.39초. 실행 신원과 종료 확인 | 다음 조건으로 진행 가능한 승인된 반례. 같은 원인이라는 증명은 아님 |
| C: B + 루트 디렉터리 자체의 data 읽기 | 준비 전용 모의 작업자(inert)의 ready 확인, 제품 정지 후 SIGTERM과 종료 확인, 약1.40초 | 이 OS·전용 runtime·정확한 정책 조합에서 통과 |
| C의 문서 흐름 | 읽기·쓰기·링크·GFM·주장 검사5단계, 약8.69초 | 실제 sandbox 실행 통과. Work는 active, 수락 없음 |
| Claude 조회 | 정확한 읽기 명령1회, 약12.82초, 파일·기록 무변경 | 시험 문맥을 제공한 조건에서 통신·최종 의미 통과. 요청 모드는 미적용(init: default) |

Claude는 완료 상태이며 새로 수락할 것이 없다고 설명했다. 기존 보고서의 집계·개선 후보·남은 회의 결정도 맞았다. 제품 adapter의 기존 상태 의미를 시험 문맥에 제공했으며, 특정 Work의 정답을 미리 알려주지 않았다. 답변이 다소 긴 점은 남아 있지만 내부 식별자·해시·개인 경로와 중복 수락 요청은 없었다. 제품 adapter나 수락 구현을 바꾼 결과가 아니다.

## 소스 반영과 근거 범위

- `runtime/official/worker.sb.in`: 성공한 C 후보의 정확한 바이트를 반영했다. 추가 읽기는 지정 OS cache 경로의 metadata, 확인한 cache 파일·디렉터리의 data, 루트 자체의 DIRECTORY data다. 홈이나 루트 하위 전체 읽기·네트워크·새 쓰기·새 실행 권한은 추가하지 않았다. 루트/디렉터리 이름은 볼 수 있으므로 이 노출을 숨기지 않는다.
- `tests/test_foundation_worker_plan.py`: 추가 규칙이 정확한 OS 경로에 한정되고 재귀 읽기나 외부 개발 runtime 의존을 추가하지 않는지 검사한다. 읽기/검사와 쓰기의 분리, 리소스 일치, 프로젝트/runtime 겹침 거부를 유지한다. 집중6개 통과.
- 새 조건 진행 검사6개 통과. 기존 연결부 검사20개와 준비/정지 검사5개를 확인했다. 스트림/결과 보호 검사는25회 실행이지만 상속에 의한 중복을 포함하므로 독립25개라고 합산하지 않는다. 기존 source 입력5개와 변경 없는 핵심 실행기44개 근거를 재사용한다.
- 오프라인 준비에서 기존 모듈·도움말 파일 누락을 발견했다. 보존된 자료로 연결하고 영향을 받은 검사만 완료했다. 이 준비 오류와 원래 실제 실패 기록을 지우지 않았다.

관측 환경은 macOS27.2(build26B123), Darwin27.2.0, arm64이며 cache 파일군은 arm64e다. C와 B의 차이는 루트 DIRECTORY 읽기 하나다. 이번 관측에서 C만 통과했지만, 그 결과만으로 B의 모든 규칙이 필수인지, 거부된 syscall/경로가 무엇인지 또는 다른 OS에서 충분한지 확정하지 않는다. 앞선 넓은 정책의 모든 예외를 복원하지 않았고 개인 개발 도구 경로도 되살리지 않았다. 정확한 cache 파일 목록은 OS별로 달라질 수 있으므로 이 template를 보편적인 공개 최소 정책이라고 선언하지 않는다.

Claude는 기존 구독 경로의 새 CLI 대화로 실행했고 보존한 init의 사용 가능 도구는 Bash 하나, MCP 없음이며 실제 호출도 승인한 Bash 명령1회였다. 스트림 parser가 init의 도구 목록·모드를 별도로 강제 검증한 것은 아니다. 요청 모드와 달리 init은 default를 보고했다. 따라서 manual 모드나 OS sandbox를 검증했다고 말하지 않는다. 허용된 단일 도구 호출과 전후 무변경을 감사한 협조적 행동 시험이다. 한 번의 성공은 전체 모델 신뢰도나 데스크톱/설치본 지원 증명이 아니다.

실제 설치·호스트 권한/설정·키·알림·커밋·공개는 수행하지 않았다. 원래 실패·후보별 실행 조건·결과·검토 원문은 후속 판단과 복구 소비자가 끝날 때까지 보존한다.

## 리뷰

계획 리뷰는 과장된 인과 추론 금지, 최종 의미 별도 확인, 디렉터리 이름 노출 명시와 리뷰/행동 예산 분리를 요구했다. 모두 반영하거나 기존 분리 근거로 확인했다. 결과 리뷰는 fixture 범위의 근거로 인정하되 설명·근거 연결을 보완하라고 했다. 새로운 실행이 필요한 지적은 없었다.

### 결과 리뷰 처분

- 문서 실행 기록의 grant에 남은 Python digest는 고정한 전용 binary와 같고, profile digest는 선택한 C 후보 및 현재 소스 template와 같다. 그 profile SHA-256은 `4eee8665a18ebb7b2827b1a9eb7936d36c7526d359f81036f5992ef8502ac6aa`다. 실행 argv도 그 binary를 지정한다. 다만 child의 `sys.prefix`는 별도 출력으로 수집하지 않았으므로 prefix를 직접 관측·검증했다고 주장하지 않는다.
- runtime 감사 목록은 기존 manifest의 predecessor hash로 고정돼 있다. 감사 root는 archive root이고 Python root는 그 하위 `python`이며,1701개 member가 모두 그 경계 안의 상대 경로임을 오프라인 대조했다. 이는 리뷰에 빠진 입력이었으며, root가 서로 같아야 한다는 제안은 이 목록 구조에는 적용하지 않는다.
- 성공 문서 fixture도 child가 보존하도록 설정했다. DB·문서2개·실제 profile/spec5개가 남아 있음을 확인했다. 삭제됐다는 리뷰 추정은 반박하고 원본을 그대로 유지했다.
- 제품 source에는 같은 상태 지침이 있지만 이번 시험은 문맥을 직접 제공했다. 설치본 진입에서 에이전트가 그 지침을 실제로 읽는 경로는 검증하지 않았다.
- 오프라인 준비에서 빠진 입력은 비공개 시험용 `fixture_wrapper.py`와 Codex 도움말2개였다. 기존 동일 작업 자료에서 연결했고 경로·hash·준비 실패는 비공개 근거에 기록했다. 제품 설치 파일을 추가한 것이 아니다.
- 다음 live 시험 전의 실행기 보강 후보: child의 Python/prefix/profile 직접 대조, init의 실제 모드·도구 목록 판정, runtime 감사 목록의 archive-root/하위-root 및 안전 상대 경로 검사, 신호 전 신원 재확인·미지원 신호 이름 거부·부모 PID 확인. 이번 성공 기록을 소급 수정하거나 새 실행하지 않는다.

소스 반영 후 예전 실행 manifest가 source-drift로 재실행을 거부하는 것은 의도한 상태다. 두 리뷰는 새 Claude CLI 대화에서 도구 없이 수행했고 입력 drift가 없었다. 리뷰 verdict는 Owner 수락을 대신하지 않는다.
