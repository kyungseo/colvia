## 수락한 범위

한 장치의 로컬 프로젝트에서 Work 하나와 승인된 한 단계를 맡긴다. 제출 프로세스가 종료된 뒤에도 단회 작업자가 실행되고, 필요한 답과 최종 결과는 해당 Work의 수신함에 남는다. 지원 단계는 작업 현황 요약, 이미 준비한 로컬 변경 결과의 검토 제출, 공식 macOS 프로필에서 별도로 승인된 문서 실행 위임이다. 첫 두 단계의 설치형 CLI를 실행 관측했다. 공식 실행 연결은 이번 후보에서 실모델로 끝까지 실행하지 않았다.

사용자는 “맡긴 작업에 질문이나 결과가 있어?”라고 물으면 된다. 답이 필요한 접수는 같은 Work의 현재 질문에 응답해야 이어진다. 기한이 지나면 기존 결과를 대조한다. 작업자가 사라지고 반영 여부를 판별할 수 없는 경우에는 명시적으로 미확인 종결한 뒤 다른 작업을 맡길 수 있다. 기기 알림은 일반 안내이며, 접수의 결과와 사용자가 열람했는지는 구분한다.

## 비차단 발견

- **N1 통지 상태기계:** `pending → attempted(OS 호출 전 기록) → api_ok | api_err` 순서로 둡니다. 재시작 시 `attempted`인데 결과가 없으면 **재전송하지 않습니다**(at-most-once). inbox가 진실 원천이고, "실제 수신"은 별도 필드(`observed`, 수동 관측만)로 둡니다.
- **N2 알림 내용:** 고정 문구만 씁니다. Work ID 원문 대신 짧은 불투명 핸들을 권장합니다. 클릭 동작은 `view <handle>` 정도로만 둡니다.
- **N3 설정 거부:** 알림 권한이 거부되면 재시도 루프를 돌지 않습니다. View와 inbox에 "OS 알림 꺼짐"을 한 번만 표시합니다.
- **N4 macOS 분리:** `setsid`, stdio를 `/dev/null`과 로그 파일로 재지정, SIGHUP 무시를 적용합니다. `osascript` 알림은 앱 귀속이 다르게 표시되므로, 문서에서 "API 성공 ≠ 표시"를 명시합니다.
- **N5 scope 경로:** 신뢰 사용자라도 합성 문서 안의 symlink로 scope를 벗어날 수 있습니다. `realpath` 이후 접두사 검사를 합니다.
- **N6 결과 보존:** 제출은 append-only 버전으로 하고, 수락은 사용자 동작으로만 합니다. 재접수나 대조 해소가 기존 결과를 덮어쓰지 못하게 합니다.
- **N7 inbox 동시성:** SQLite WAL 또는 잠금 + append를 쓰고, 파일 권한은 0600으로 둡니다. 이벤트 `event_id`에 유일 제약을 걸어 중복 이벤트를 흡수합니다.
- **N8 중단 UX:** `stop`은 요청 레코드만 씁니다. 단계 경계에서 반영하며, 진행 중인 단계의 효과가 불명확하면 `대조 대기`로 표시합니다.

`one_active` 인덱스는 `reconcile`도 활성 상태로 셉니다. `inspect`는 양성 복구에 성공했을 때만 이 상태를 해소합니다. 그런데 효과가 확실히 없었던 경우에도 `reconcile`로 들어가는 경로가 세 가지 있습니다.
- **a. 실행 전 취소:** `_step`의 fence에서 취소를 감지하면 `stopped-before-effect`를 반환하지만 행은 `reconcile`, `used=1`로 남습니다. 효과 전이 확실하므로 `WHERE phase='reconcile' AND epoch=?` 조건으로 `stopped`로 확정해야 합니다.
- **b. 실행 전 재검증 실패:** 기한 만료나 범위 변경으로 `_delivery_validate`가 실패해도 `_delivery_report`와 같은 `except Exception`에 묶여 `reconcile`이 됩니다. try 범위를 효과 전과 효과 후로 나누고, 효과 전 실패는 `stopped`로 처리해야 합니다.
- **c. 실행 프로세스 생성 실패:** `_delivery_command`의 `OSError`는 `used=0`인데도 `reconcile`로 바뀝니다. 이 경우 `stopped`로 처리하거나 `queued`를 유지해 재기동해야 합니다.

**2. 만료되었거나 실행 프로세스가 사라진 `queued`/`question` 행(`used=0`)이 영구히 남습니다**

- `_delivery_public`은 이런 행을 `reconcile`("문서 반영 상태 확인")로 표시합니다. 효과가 없었는데 그렇게 안내하는 것은 오해를 부릅니다.
- `inspect`는 `used==1`인 행만 다루므로 DB에는 활성 행이 그대로 남고, 새 접수가 계속 막힙니다.
- 실제로 이런 상황이 생기는 경우:
  - 절전·로그아웃 중 실행 프로세스가 종료됨
  - Job 종료로 실행 프로세스가 강제 종료됨
  - update/rollback 직후 실행 프로세스가 구 모듈을 실행함
- 처리 방안:
  - `inspect`에서 `used=0`이고 만료된 행은 `stopped`로 확정합니다.
  - 아직 만료되지 않은 `queued`는 같은 epoch로 재기동합니다. `BEGIN IMMEDIATE`와 `phase/epoch/used` 가드가 있어 중복 실행은 생기지 않습니다.

**3. 제출 결과를 양성 기록으로 복구하는 조건이 지나치게 좁습니다**

- `submit` 복구 조건은 `graph["current"]`가 해당 selection이고 `state=="review"`인 경우뿐입니다. 사용자가 검토를 마치고 다음 단계로 넘어가면, 제출 기록이 남아 있어도 복구할 수 없습니다.
- selection 존재, `operation_id` 일치, `revision_ref` 일치만으로 양성 증거로 인정하면 충분합니다.
- `execute`에서 `read_capsule`이 예외를 내면 `inspect` 전체가 실패합니다. 이 예외는 "증거 없음"(`None`)으로 처리해야 합니다.

**4. 기본 View가 수신함 오류 때문에 통째로 실패할 수 있습니다**

기본 View는 `(OSError, ValueError, ContractError)`만 잡습니다. 다음 예외들은 잡히지 않습니다.
- **`sqlite3.Error`:**
  - `O_EXCL`로 파일을 만든 뒤 `CREATE TABLE` 전에 중단되면 `no such table`이 발생합니다.
  - `mode=ro`로 열 때 hot journal이 있으면 쓰기 불가 오류가 발생합니다.
  - 잠금 시간이 초과될 수 있습니다.
- **`KeyError`:** 알 수 없는 phase가 있을 때 `_delivery_public`의 `messages[state]`에서 발생합니다.

조치:
- 위 예외를 기본 View와 `view inbox` 양쪽에서 잡고 "수신함 확인 필요" 안내로 대체합니다.
- 테이블 없음은 빈 수신함으로 취급합니다.

**5. (확인 필요) 활성 delivery가 있을 때 update/rollback/detach를 막는지 확인해야 합니다**

수신함은 의도적으로 inventory 밖에 있습니다. 따라서 `running` 중 모듈이 교체되거나, 구 릴리스로 돌아간 뒤에도 활성 행이 남을 수 있습니다. 전환 명령이 활성 행을 거부하는지 확인이 필요합니다.

## 비차단

- **중복 실행 방어:** `_step`의 `UPDATE … SET phase='running',used=1 … AND used=0`에서 `rowcount`를 확인하지 않습니다. 현재 흐름에서는 도달할 수 없지만, 1단계 불변식을 지키는 마지막 방어선이므로 `rowcount!=1`이면 반환하도록 하는 것이 좋습니다.
- **절전과 기한:** 재검증과 `_delivery_report` 사이에 절전이 끼면 기한이 지난 뒤 `publish`가 실행될 수 있습니다. 효과 직전에 기한을 한 번 더 확인하는 것이 좋습니다. `execute`는 `expires_wall_ns`가 있어 상대적으로 안전합니다.
- **폴링 경로:** 상태 조회를 `start`로 하면 생성 모드와 `BEGIN IMMEDIATE` 쓰기 잠금을 거칩니다. 테스트를 포함해 `inspect`나 읽기 전용 경로를 쓰는 것이 좋습니다.
- **`summary`의 `reconcile` 처리:** 요약은 읽기 전용이므로 만료를 기다리지 않고 바로 `stopped`로 처리해도 됩니다.
- **입력 검증:** `execute` 페이로드의 `spec["request"]`를 타입 확인 전에 인덱싱합니다. 그래서 계약 오류가 아니라 `TypeError`/`KeyError`가 발생합니다.
- **View 안내:**
  - `view inbox`의 질문 행에 `question_id`와 계속/중단 명령이 없어 화면만 보고는 응답할 수 없습니다.
  - 기본 View는 최신 1건만 보여주고, 알림 `unavailable`은 표시하지 않습니다.
  - 행 하나가 손상되면 목록 전체가 실패합니다.
  - 요약 결과의 `view[:32768]`은 줄 중간에서 잘립니다.
- **알림:**
  - 알림 문구가 macOS는 한국어, Windows는 영어로 서로 다릅니다.
  - 알림 도중 프로세스가 끝나면 `notice='attempted'`로 고정되고, 이를 따로 표시하지 않습니다.
- **기타:**
  - macOS에서 launcher를 직접 실행하는 조건이 `sys.version_info==(3,14,10)`에 묶여 있어 취약합니다.
  - `normcase`는 macOS의 대소문자 무시 볼륨에서 같은 프로젝트를 다른 수신함 키로 만들 수 있습니다.
- **테스트:**
  - 반환값의 `submit_once: True`는 실제로 검증되지 않습니다. `publish`가 멱등이면 두 번 호출되어도 통과합니다.
  - 다음 경로가 없습니다: 중단, 만료, 실행 프로세스 생성 실패, `reconcile`의 양성 복구, 알림 기록, 기본 View의 수신함 오류.

## 문제없음으로 판단

- 접수 키가 plan digest에 묶여 있고, `ask`/`notify`/`expires`가 승인 대상에 포함됩니다.
- 질문 단계에서는 `used=0`이고, 답변 시 재검증 후 epoch를 올려 실행 프로세스를 하나만 둡니다.
- 효과 이후의 최종 갱신은 `phase/epoch` 조건으로 막혀 있고, 불확실한 효과는 보존됩니다.
- 알림 갱신은 epoch 조건으로 보호되어 답변이나 중단과 경합하지 않습니다.
- 수신함은 프로젝트 스냅샷 밖에 있고, 파일 종류·링크 수·권한을 확인합니다.

## 수락 차단 결함

**B-1. 예약 후 증거 없는 행은 끝나지 않음**

- **상태:** submit 접수가 `phase='running', used=1`인 상태에서 `_step` 프로세스가 `publish` 전에 죽은 경우입니다. 강제 종료, 전원 차단, 또는 latest 확인과 publish 사이의 `stop` 경합으로 생깁니다.
- **재현:**
  1. 격리 저장소에서 `UPDATE delivery SET phase='running', used=1, expires=1`로 행을 만듭니다(제출은 하지 않음).
  2. `handoff inspect`를 실행합니다. 복구 결과가 `None`이고 submit이므로 행이 그대로 유지됩니다.
  3. `handoff stop`을 실행합니다. 행이 `reconcile`이 됩니다.
  4. 다시 `inspect`해도 변화가 없고, `stop`은 `reconcile`에 대해 아무것도 하지 않습니다.
  5. 이 상태에서 새 `handoff start`는 `one_active` 위반, `update`/`rollback`/`detach`/`repair`는 `require_delivery_idle`로 영구 거부됩니다.
- execute도 같은 문제가 있습니다. capsule이 completed가 아니면 같은 상태에 갇힙니다.
- **최소 수정안:** 사람이 명시적으로 닫는 경로 하나만 추가합니다. 자동 재시도는 아닙니다.
  - `stop`에서 `used=1`, `phase='reconcile'`, `expires <= now`일 때 `writer_guard` 안에서 `_delivery_recover`를 다시 실행합니다.
  - 복구되면 `done`으로 기록합니다.
  - 복구되지 않으면 새 종결 상태 `unresolved`로 옮깁니다. 이 상태는 `one_active` 인덱스와 `require_delivery_idle`의 phase 목록에서 제외하고, 메시지는 "효과를 확인하지 못한 채 닫았습니다. 다시 실행하지 않습니다. Work 기록을 확인하세요."로 둡니다.
  - `inspect`는 `unresolved`에도 `_delivery_recover`를 허용해, 나중에 양성 증거가 나타나면 `done`으로 올립니다.
- **회귀 테스트:** 위 주입 상태에 대해 `stop` → `unresolved` → lifecycle 허용 → 효과 미중복을 확인하는 테스트 1개를 추가합니다.

## 같은 경로의 보조 지적 (B-1과 함께 고치기 권장)

**B-2. 복구의 조상(ancestor) 조건이 과합니다.** 제출된 선택이 현재 선택의 조상이 아닌 경우, 즉 Work가 종료되어 `current`가 `None`이거나 검토 반려로 형제 선택이 생긴 경우에는 실제 제출 기록이 있어도 복구되지 않습니다. 그러면 B-1 상태에 빠집니다.
- 선택 레코드가 불변이라면 다음 대조만으로 양성 증거가 됩니다. 이 경우 조상 탐색을 제거하는 것이 최소 수정입니다.
  - `selections[selection_id]`가 존재
  - `operation_id`가 일치
  - `revision_ref`가 일치
  - 저장된 revision 원문이 일치
- 조상 탐색을 유지한다면, 그 안의 `KeyError`가 `inspect`의 `except`에 걸리지 않는다는 점도 함께 고쳐야 합니다.

## 수락과 무관한 권고

- `require_delivery_idle`가 `sqlite3.Error`를 감싸지 않습니다. 손상된 DB에서 lifecycle은 거부되지만(fail-closed) 원시 예외가 노출됩니다. `delivery_inbox`처럼 `COLVIA-INBOX`로 감싸는 편이 좋습니다.
