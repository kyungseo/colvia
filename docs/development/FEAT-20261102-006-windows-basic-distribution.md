## 비공개 ARM64 후보의 첫 설치

로컬 Go 1.27.2 표준 라이브러리로 ARM64 실행 파일을 오프라인 빌드했다. 시스템 Python을 검색하지 않는 합성 프로젝트에서 고정 upstream ZIP으로 전용 Python을 준비하고 같은 파일을 재사용했다. 한글·공백 경로의 설치 미리보기·확인값 적용·status·start·View·빈 상태 resume가 종료 코드 0을 반환했다. 확인 대상 Python 등록 키와 PATH, 원본 문서가 같았고 Job 잔여는 0이다. 공개 다운로드·SmartScreen 통과·실제 사용자 설치와 Work가 있는 재개는 이 결과에 포함되지 않는다. 호스트 기본 Python의 AST 호환 오류와 검사기의 환경 변수 대소문자·전송 폴더에 있던 검사 전용 python.exe 발견은 실패로 보존했다. 두 게스트 실패는 설치 명령 호출 전이었고 Job 잔여는 0이었다. 빌더에는 기존 호스트 Python 3.14.7을 사용했다.

## 첫 Work 쓰기와 재개 지점

직전 관리 payload와 현재 관리 코드 조합에서 이전 후보 준비·설치 미리보기·적용까지 통과했다. 첫 intent draft 요청은 종료 코드 65, `HV2-WORKSPACE-PRODUCT`로 거부됐다. 관리 모듈이 설치된 CLI를 직접 불러온 탓에 실제 Python 주 프로그램이 프로젝트의 제어 런처와 일치하지 않았다. 보호 검사에서 중단했으며 쓰기 재시도는 0회다. 검증 Job 종료 1, 잔여 프로세스 0. 현재 후보와 이전 후보의 관리 모듈 바이트가 같으므로 수정 대상은 공통 진입점이다.

Driver는 기존 모듈·바인딩 대조를 유지하고 검증된 프로젝트 런처를 전용 Python `-I -B`의 실제 진입점으로 실행하도록 관리 소스를 보정했다. 프로젝트 런처 바이트와 관리 도구의 독립 사본을 대조하고 중첩된 target은 거부한다. 실제 자식 실행 인수·반환값, 런처 불일치·다른 target 거부의 오프라인 회귀검사 2건 통과. 보정 후 Windows 후보의 쓰기 성공은 미관측이다.

후속은 보정한 관리 후보로 지정 VM의 보존 프로젝트·바인딩·초안 미작성 여부부터 읽기 전용으로 대조한 뒤 첫 초안에서 재개한다. 동일 Work의 승인과 기록 보전, 정상 인용·링크 편집, 갱신·롤백·복구·제거, 변조·busy handle·reparse·부분 진행, 모델 행동과 최종 Claude 결과 리뷰가 남았다. 시험에서 사용한 Go는 공급자 빌드 전용이다. 비공개 파일 전달 방식의 차이, 실제 다운로드 보호 정책·서명과 배포 고지는 공개 전 별도 확인 대상이다.

지정 VM은 일반 사용자 콘솔에서 정상 종료했다. 네트워크 장치·클립보드 원복 후 전체 설정이 원본과 바이트·모드 모두 일치했다. 재개·리뷰용으로 제품 작업 트리와 정확한 입력·결과 및 개발 후보를 보존한다. 외부 증거와 분리한 비공개 운영 런북에는 성공한 단계와 종료·원복 조건만 요약했다.

## 보정 후 네이티브 관측

보존한 이전 버전 프로젝트의 바인딩·런처·문서, 첫 intent 및 Work 미작성 상태를 대조했다. 지정 표준 계정에서 보정 관리 후보로 첫 초안→합성 승인→Work 시작→새 프로세스에서 같은 Work 조회→인용·링크 문서 결과 제출을 마쳤다. 이전 payload에서 현재 payload로 갱신하고 롤백했다. 이전 payload와 짝지은 관리 도구로 손상 런처 복구와 프로젝트 연결 해제까지 진행했다. 16개 명령 종료 0, 조회·갱신·롤백·복구·제거 과정에서 검사한 Work/intent 파일 13개의 바이트와 편집·보존 문서가 기대값과 일치했다. 제품 코드의 결과 수락과 외부 모델의 독자적 수행은 별도다.

별도 합성 폴더의 9단계에서 변조 ZIP, junction 경유 입력, 공유가 금지된 열린 파일을 예상대로 거부했다. 설치 계획 기록 직후 중단을 주입했고, partial 상태에서 같은 요청 원본과 확인값으로 복구해 상태가 pass가 됐다. 앞선 프로젝트는 그대로였다. 두 Job의 종료는 0, 잔여 프로세스 0. 게스트 정상 종료 후 네트워크·클립보드를 복원해 전체 VM 설정 바이트와 파일 모드를 원본과 대조했다. 실제 정전·다운로드 보호 정책·실사용 효과는 미관측이다.

- **재현 조건:** `--request C:\proj\..\proj\req.json`처럼 `..`이 들어간 경로나 `PROJEC~1` 같은 8.3 단축명을 쓰면 됩니다. `absolute()`는 경로를 정규화하지 않으므로 `is_relative_to`와 `.hrn` 검사를 통과하고, 요청 파일이 프로젝트 안에 기록됩니다.
- **최소 수정:** 기존 조상 reparse 거부는 그대로 둡니다. 그 뒤 `parent = path.parent.resolve(strict=True)`로 실제 경로를 얻고, `parent`와 그 조상 중 `target`과 `samefile`인 것이 있으면 거부합니다. `.hrn` 검사도 `resolve`된 parts 기준으로 바꿉니다.
- **집중 검사:** `..` 경로, 단축명, 대소문자만 다른 경로, 프로젝트 밖 정상 경로를 각각 확인합니다.

**P3: 실패 시 임시물 잔존**
- `publishSlot`은 해시 불일치·ZIP 오류·`MoveFile` 실패 시 `.pending-*` 디렉터리를 남깁니다.
- `save_request`는 대상이 이미 있으면 rename이 실패하고 `.pending-*` 파일이 남습니다.
- 기존 상태를 훼손하지는 않지만 복구 흔적이 누적됩니다.
- **수정:** 직접 만든 stage와 pending만 실패 경로에서 `RemoveAll`/`unlink`합니다.
- **검사:** 잘못된 ZIP과 기존 요청 파일 충돌 후 잔여물이 0인지 확인합니다.

## 남는 조건 (코드 결함 아님)

- **verify:** manifest에 없는 추가 파일을 거부하는지 발췌만으로는 확인할 수 없습니다.
- **TOCTOU:** `plain`→`Open`, verify→exec 사이의 경쟁 조건은 신뢰 계정 전제에서만 수용 가능합니다.
- **잔류 lock:** 강제 종료 후 lock이 남으면 수동으로 확인해야 합니다.

## Owner 수락과 완료 (2026-11-03)

지정 Windows 11 ARM64 VM의 표준 계정에서 비공개 공급 파일로 전용 Python을 준비하고 프로젝트를 연결했다. 선행 후보에서 첫 Work와 View, 새 프로세스의 같은 Work 재개, 버전 갱신·롤백, 복구 및 프로젝트 연결 해제까지 확인했다. 연결 해제 뒤에도 문서와 작업·승인 관련 파일 13개가 보존됐다. 제거 범위는 프로젝트 연결이며 전용 Python 및 사용자 데이터는 남는다.

마지막 후보는 요청 저장 경계만 바뀌었다. 이 후보의 실제 관리 명령으로 8단계를 확인했다. 정상 외부 폴더의 새 이름에는 미리보기를 저장했다. 상위 이동, 대소문자 변형, 프로젝트의 실제 NTFS 단축 이름과 보호 폴더 `.hrn`의 원래 이름·실제 단축 이름은 모두 거부했다. 기존 이름으로 다시 저장해도 원본 바이트는 같았고 남은 임시 파일과 예기치 않은 프로젝트 쓰기는 각각 0건이었다. 검사 종료 코드 0, 잔여 프로세스 0. VM은 정상 종료했고 시험 전 설정 파일과 바이트·권한이 일치했다.
